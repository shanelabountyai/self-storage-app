# Self-Storage Business Application

Multi-facility self-storage platform. Learning project, built to professional standards.

## How to work in this repo

- Product source of truth: `docs/prds/`. Build order: `docs/prds/06-backlog.md`, top to bottom, one item (or noted small cluster) per session. To find what is next without reading 88k tokens of wide table, read the generated `docs/prds/06-backlog-index.md` — it leads with the open items. Then read the full row in `06-backlog.md` for the one item you are about to build; that row is still the source of truth.
- `docs/prds/07-decisions.md` OVERRIDES any conflicting PRD text. Never re-open a settled decision; append new decisions there instead.
- Stack: Next.js (App Router) + TypeScript, Postgres + Prisma, Stripe (ledger-driven PaymentIntents — NOT Stripe Billing, per D-6), Tailwind CSS, deployed on Vercel.
- Data model: use the canonical entity names in `docs/prds/00-master-prd.md` §7 (Facility, Unit, UnitType, Tenant, Lease, Invoice, Payment, AccessCredential, Lead, and supporting entities).
- Money is integer cents. All timestamps UTC in the DB, facility-local timezone for display.
- Compliance defaults are Texas, built per-state configurable (D-10). All legal/notice text is draft-only and not legal advice.
- Gate hardware runs against the simulated adapter (PRD 03) — never assume a real vendor API.
- Accessibility: WCAG 2.1 AA is an acceptance criterion on customer-facing work, not a later cleanup.
- After completing a backlog item, in this order: run tests → mark the item ✅ in `docs/prds/06-backlog.md` → append its entry to `docs/progress/` and run `npm run docs:index` → commit → **push**. If the item shipped anything a customer touches, **re-read `apps/web/app/(public)/accessibility/page.tsx` before the commit** — it is a public claim about the codebase, so it goes stale on merges rather than on edits, and it went false in BOTH directions in twelve days (disclaiming checkout and payments as "not built yet" once they had shipped, while still claiming automated scans on "every page" and recorded screen-reader passes that had never happened). An overstated statement converts a fixable bug into an alleged misrepresentation; an understated one publicly certifies that the money path was never assessed. The SHA follow-up commit gets pushed too. Committing without pushing leaves the work on one laptop; this repo sat 123 commits ahead of an empty remote for a week before anyone noticed.
- **The build record is split: `docs/progress/` holds the entries, `docs/PROGRESS.md` is a generated index over them.** One entry per completed item, appended as a `### ` heading to the **highest-numbered** file in `docs/progress/` (start a new part once the current one passes ~90 KB), with its commit SHA on the line directly below the heading and three things: **what it built**, **what it decided** (choices a later session must not silently reverse), and **what it left behind** (deliberate gaps and which item owns them). Note any real bug found along the way. Keep it factual — it is a record, not a changelog of intentions. Then run `npm run docs:index`.
- **Never hand-edit `docs/PROGRESS.md` or `docs/prds/06-backlog-index.md`** — both are generated, and the edit is silently lost on the next run. Edit the part file, or `06-backlog.md`, and regenerate. It was one 1.63 MB file until 2026-09-05: 580k tokens, several times any context window, so no session could read the record it was told to append to, and every session paid again for whatever slice it pulled back. To read one past entry, `npm run docs:entry -- B-137` — about 2k tokens, against 30k for the part file it lives in.
- Record the SHA in a small follow-up commit, not by amending. Amending changes the SHA you just wrote down, leaving `PROGRESS.md` pointing at a commit that no longer exists.
- **Merge a PR with `gh pr merge --rebase`, never `--squash`** — for the same reason, and it is the easier mistake to make because the merge happens hours after the SHA was written. A squash collapses the branch into one new commit and orphans every SHA on it, so each `PROGRESS.md` entry the branch carried now names a commit reachable from nothing. It cost B-218 and B-202 their recorded SHAs on 2026-08-29, and `main` has no merge commits in its history precisely because every item before them landed with its own commits intact. If a squash has already happened, do not rewrite `main` to undo it: correct the affected `PROGRESS.md` entries to the squash SHA and say in the entry what the original was.
- **`--rebase` rewrites the SHAs too — check `PROGRESS.md` against `main` after every merge, not just after a squash.** GitHub re-creates each commit as it replays it, so the SHAs change even when the branch was already fast-forwardable and nothing needed replaying: PR #19 merged on 2026-08-30 with `main` sitting on the branch's own parent, and B-204's `40ee469` still became `3d6b6c4`. `--rebase` is still the right flag — it keeps one commit per commit, so the fix is a one-line correction rather than a whole entry's worth of SHAs pointing at nothing — but the entry is stale the moment the merge lands. The remedy is the squash one: `git log --oneline` on `main`, correct the entry, name the pre-merge SHA in it, and push. Do not rewrite `main`.
- **`npm run docs:audit` after a merge; nothing else checks this.** `docs:index` regenerates the index without verifying that a single SHA it names exists. The audit resolves every recorded SHA against `git` and `origin/main`, and it exits non-zero, so it is the one thing worth running before you call an item recorded. It is how B-205's three orphaned SHAs were found on 2026-09-05, six days after B-204's identical breakage — from the same merge, in the entry directly below it — was spotted and fixed by hand while B-205 was left alone. Two deliberate quiets: it reads only the LEADING backticked run of an entry's SHA line, because the pre-merge SHA a corrected entry quotes in prose afterwards is supposed to be gone; and a commit that exists but is not yet on `main` prints as a note and does not fail, because that is every entry you write on a branch. Only a SHA resolving to nothing fails the run — which is exactly what a merge that rewrote it looks like.
- **`git fetch` before you branch, and check you are actually on `main`'s head.** A session container is cloned once and can be days old; this one was six days and **117 commits** behind, and `PROGRESS.md` had grown 354 KB and 54 entries in the gap. Work built on that base looks clean locally and silently deletes everything added since. `git rev-parse origin/main` against `git ls-remote origin main` is the check, and it takes a second.
- **`gh pr merge --auto` merges immediately when auto-merge is not enabled on the repo.** It does not error and it does not queue; #19 went into `main` with `verify` still in progress and e2e never having run on the PR at all (`mergeStateStatus` was `UNSTABLE`, which is what that reads like). If the point is to wait for CI, wait for CI — `gh pr checks --watch` — or enable auto-merge in the repo settings first.
- Also update the same-day PRD when an item settles something the PRD left open, and append owner decisions to `07-decisions.md` with a new D-number rather than resolving them silently.
- Commit after every completed item with a message like `B-012: unit CRUD`, then push.

## This project owns :3000, and its cleanup must not reach other projects

**`baseURL` is hardcoded to `localhost:3000` in `playwright.config.ts`**, so this repo cannot move off port 3000 without an edit — it is the incumbent, and every other project is allocated around it (the port map lives in the global `~/.claude/CLAUDE.md`).

**The pre-sweep cleanup must be anchored to `$PWD`:**

```bash
pkill -9 -f "$PWD.*playwright"      # NOT `pkill -f playwright`
lsof -ti :3000 | xargs -r kill -9
```

A bare `pkill -f playwright` matches **every project on the machine**, not this one. It killed the rental platform's test runs twice on 2026-08-15 while a sweep was running here — a clean SIGKILL partway through, no failures, no summary, which reads exactly like a broken build on the receiving end. The reverse can happen to this repo just as easily.

**The tell that separates a cross-project kill from a memory kill is which process died.** Jetsam takes the LARGEST process, which is the server. A `playwright` pattern takes the RUNNER and leaves the server listening. A dead runner beside a healthy server is positive evidence that something on the machine did it — check `lsof -ti :3000` before reaching for `/Library/Logs/DiagnosticReports/JetsamEvent-*.ips`.

## Pull requests

- **Always open a PR as a draft**: `gh pr create --draft`. Mark it ready (`gh pr ready`) only when the feature is complete and the local suites are green.
- **Why:** the full e2e + Lighthouse run is ~30 minutes of Actions time, and it is meant to be spent on PRs that are actually up for review.
- **CI is split into two lanes to make that pay off** (`.github/workflows/ci.yml`, 2026-08-15). `verify` runs on every PR push — lint, typecheck, unit, build, schema drift. `e2e` runs only on merges to `main` or when `github.event.pull_request.draft == false`, and carries a 60-minute cap because the job previously had no timeout at all and inherited GitHub's six-hour maximum. `paths-ignore` skips both lanes for `**.md` and `docs/**`.
- **The demo seed belongs to the heavy lane only.** `npm run db:seed:demo` is what the e2e suite asserts against by name; the unit suite creates its own fixtures and needs none of it (locally it runs against `storage_test`, which has only roles and permissions). Moving it out of the fast lane is safe for that reason and no other — if a unit test ever starts depending on demo data, it will pass locally and fail in CI.

- **Adding a dependency breaks esbuild until you `npm rebuild esbuild`.** `package.json` gates install scripts behind `allowScripts`, and `npm install <pkg> --workspace web` re-links `node_modules` without re-running the gated postinstall that puts esbuild's platform binary where its JS wrapper looks for it. Every `npm test` then dies in `bundleConfigFile` with a stack that names vite and esbuild and never says why — the real line, several frames down, is *"You installed esbuild for another platform than the one you're currently using"*, which is false and sends you looking at your architecture. `npm rebuild esbuild` fixes it in seconds. Cost B-106 its first ten minutes.

## Four rules this codebase learned the hard way

- **A new column that configures behaviour gets its control in the same item.** Each one is individually defensible to defer, and they accumulate: `billingPolicy`, `invoiceLeadDays`, `prorateOnMoveIn`, `paymentRetryDays` and the late-fee ladder all shipped reachable only from a database client, and took two separate clean-up passes to close. If an operator would ever need to change it, it needs a form field before the item is done.
- **`db:migrate` authors against the LOCAL database; `db:migrate:cloud` is the only script that writes to Neon (B-253).** Until 2026-09-01 `db:migrate` was `dotenv -e .env.local -- prisma migrate dev`, and `.env.local` is the Neon **dev branch** — so the ordinary way to add a migration connected to shared cloud infrastructure. Because that branch is empty (it has none of the 107 migrations), `migrate dev` did not add anything: it announced *"We need to reset the `public` schema at ep-holy-block…neon.tech"* and offered `migrate reset`, which drops it. One keystroke at a prompt raised by a command whose documented purpose is "add a migration". It now points at `.env.test` (local Postgres, `storage_test`), which is the resettable thing and is kept in sync by `db:migrate:e2e`. **`db:migrate:cloud` uses `migrate deploy`, which only ever applies pending migrations and cannot drop anything.** `db:migrate:all` runs test → e2e → cloud in that order, and **`db:status` reports local AND cloud and exits non-zero if either is behind** — run it before assuming a migration reached everywhere, because nothing else will tell you.

- **Restart `npm run dev` after a schema change.** A running dev server holds the Prisma client it started with, so `db:generate` alone leaves it serving `Unknown field ... for select statement` while the unit tests pass — they reload the client each run. Costs twenty minutes if you go looking for the bug in your own code.
- **The test suite has its own Postgres schema; run `npm run db:migrate:test` after every migration.** `vitest.config.ts` points `DATABASE_URL` at `storage_test`, so dev keeps `public` and a test run can no longer leave a live owner account (or 3,901 facilities) in the database you are developing against. Two things make it work and both were measured: the URL carries **`schema=`** to scope the ORM *and* **`options=-c search_path=`** to scope RAW SQL, because Prisma does not set `search_path` from `schema=` — with only the first, `claimUnit`'s `FOR UPDATE SKIP LOCKED` and the gapless numbering silently read `public` while fixtures went to `storage_test`. It is built from **`DIRECT_URL`**, not the pooled one, because Neon's pooler rejects `search_path` as a startup parameter. A new migration is not applied to the test schema automatically — the suite will fail with a missing column until you run `db:migrate:test`. **The redirect is skipped when `CI` is set**, because CI's whole database is a throwaway container that migrates into `public`; pointing it at `storage_test` broke a build with "table does not exist".

- **That schema redirect is a `vitest`-only concept — Playwright needs its own migrate step, `npm run db:migrate:e2e` (B-120).** `.env.test`'s `DATABASE_URL` names a database called `storage_test`, and inside it there are TWO schemas: the `storage_test` SCHEMA vitest redirects to (above), and `public` — which is what Playwright's own Node process, `e2e/global-setup.ts`, and the built app under test (`webServer` in `playwright.config.ts`) all read directly, because none of them load `vitest.config.ts`. `db:migrate:test` never touches `public`. Skip `db:migrate:e2e` on a fresh machine and `npm run test:e2e` fails in global setup with `The table public.checkout_session does not exist` before a single spec runs — which reads like a broken app, not a missing local setup step. Run it once, and again after a new migration, the same as `db:migrate:test`; it also seeds roles/permissions and the demo facilities the specs assert against, since a freshly migrated `public` schema starts with neither.

- **The comms catalog is SEEDED state, so a template edit makes the suite disagree with your branch until you reseed (B-206).** `packages/db/prisma/seed.mts` writes `COMMS_TEMPLATES` into the schema and `npm test` never re-reads the constant, so the database keeps whatever branch last ran `db:migrate:test`. Check out `main` with a template branch still seeded and the affected suites fail with **`expected [] to have a length of 1`** — the send path resolved a template whose `requiredMergeFields` the code cannot satisfy, `renderEmail` threw, and the message was recorded `failed` instead of sent. That reads exactly like a broken sender and is a stale seed; it also means a "baseline on `main`" measured without reseeding is not one. `npm run db:migrate:test` fixes it, and it is needed when you SWITCH branches, not only after a migration — which is what makes it easy to miss, since nothing in the schema changed.

- **Appending hand-written SQL to an already-applied migration desyncs its checksum.** Prisma stores a sha256 of each migration file in `_prisma_migrations`; edit the file after it has run and the next `migrate dev` announces *"the migration was modified after it was applied"* and offers to **reset the development database**. Do not accept. The fix is to recompute the hash and `UPDATE _prisma_migrations SET checksum = ...` for that row — the schema is already correct, only the bookkeeping is stale. Better still, put the raw SQL in the migration **before** applying it: `migrate dev --create-only`, append, then `migrate dev`. `prisma migrate status` does NOT catch this, so it stays invisible until the next migration a week later (it cost B-079 its first ten minutes).

- **Anything that asserts a MARKETING message was sent must pin the clock.** `deliverForRule` refuses marketing during quiet hours (FR-MSG-5: before 8am or from 9pm, facility-local) using the real wall clock, so a suite that sends one passes between 8am and 9pm Central and fails outside it — as "expected [] to have a length of 1", which reads exactly like a broken sender. Three suites had this latent for weeks and only surfaced during a 22:00 verification run. Use `vi.useFakeTimers({ toFake: ['Date'] })` + `vi.setSystemTime(...)`; faking timers wholesale hangs the Prisma round trips. The same trap applies to SMS at any classification (`isSmsQuietHours`).

- **A long `$transaction` against Neon needs a raised timeout, and the default is not it.** Prisma's interactive-transaction default is `maxWait 2s / timeout 5s`, sized for a local database; ours is remote, and the longest transactions here make eight or nine round trips inside one. `packages/db/index.ts` sets 10s/20s. A transaction that aborts on the clock fails intermittently *only under parallel load* — passing alone, passing on the next run — so it reads as flakiness rather than as the production bug it also is.

- **A green build and a 200 on the homepage do not mean production works.** Most pages here are statically prerendered and query the database at BUILD time, so they render perfectly from a deployment whose every runtime query throws. That is exactly what shipped: the Prisma query engine was missing from the serverless bundle, `/` was 200 and every dynamic route, every API handler and the hourly cron were 500, for a day. Two settings keep the engine reachable — `binaryTargets` in `schema.prisma` generates the Linux one, and `serverExternalPackages: ['@prisma/client']` in `next.config.ts` stops Next.js bundling the client away from it. Smoke-test a deploy with something **dynamic**: `curl -o /dev/null -w '%{http_code}' "$SITE/storage/search?q=78704"`.

- **`npm run typecheck` covers `tests/` and `e2e/` too, via `tsconfig.tests.json` — keep it that way.** For most of this repo's life it did not: `apps/web/tsconfig.json` lives in `apps/web`, so its `include` stopped at the app and the repo-root test directories were typechecked by *nothing*. A test could import a name that did not exist, or build a fixture missing a required field, and the suite would still go green — Vitest and Playwright transpile per file without checking types across them. It cost B-119 a missing `AxeBuilder` import that surfaced only as a runtime `ReferenceError` under Playwright, and B-106 a fixture silently short a newly-required field. Turning the check on found **28 further errors already in the tree**, including an `Actor` fixture reaching through a union branch it had not narrowed and a delinquency step demanding a proof field (`lock_serial`) that has never been a member of `PROOF_FIELDS`.

- **Run the schema-drift check before pushing, not just the tests.** `prisma migrate diff --from-schema-datasource --to-schema-datamodel --exit-code` is what CI fails on, and `npm test` cannot see it: a migration that creates an index the model does not declare passes every local test and fails every push. That exact mistake cost six red CI runs.

- **Test isolation is not free on a shared database.** `audit_log` is append-only and never cleaned between tests, so an assertion like `findFirst({ where: { action, entityId: leaseId } })` can return a row an earlier test in the same file wrote — scope it to the specific entity (the audit context carries the ids) or order newest-first. The same applies to fixture names: twenty suites create a tenant called "Ada Renter", and `searchTenants` caps at 25 results. A suite that passes once has not been shown to be repeatable; if a test touches shared state, run the suite twice before calling it green.

- **`audit_log`'s append-only trigger doesn't just block reads getting confused — it blocks cleanup entirely, permanently (B-185).** It carries a RESTRICT foreign key to `facility` and `staff_user` plus a statement-level trigger refusing UPDATE, DELETE and TRUNCATE on itself, with no in-band override by design. Any facility or staff fixture a suite ever audit-logged against (most that exercise real admin actions) can never be reclaimed by that suite's own `afterAll` — `TRUNCATE ... CASCADE` on `facility` fails outright, because CASCADE pulls `audit_log` in and the trigger refuses it. `storage_test` accumulated 13,106 facilities this way before anyone noticed, because there is no per-suite discipline that can fix it. The only real remedy is dropping and rebuilding the whole schema — `npm run db:reset-test` does that in one command. Run it when the suite gets slow or an assertion fails for a row-count reason that has nothing to do with the code (a full-table scan timing out, a `take: N` cap filling with stale rows); it is not wired into `npm test` for the same "too slow to tax every run" reason `db:migrate:test` isn't.

- **Run one e2e spec with `npm run test:e2e --`, never bare `npx playwright test` (B-130).** `test:e2e` wraps the run in `dotenv -e .env.test -e .env.local`; the bare command does not, so `DATABASE_URL` is unset in Playwright's own Node process and **`e2e/global-setup.ts` returns at its first line**. Everything still passes — the app under test gets its own env from `webServer` — so what you lose is silent: the stale checkout locks are not released, the reservation holds are not expired, and (since B-130) the previous run's lien notices are not cleared. Debugging one spec that way and concluding the suite is repeatable is exactly the wrong conclusion, and it is the conclusion the green result invites. The tell is the absence of any `[e2e setup]` line in the output.

- **e2e's shared demo fixtures get ONE of two protections, never neither (B-120).** A full sweep against the same, un-reseeded database runs twice in a row without failing, and it stays that way because every spec that touches shared state picks one of two disciplines rather than assuming the fixture will be clean: (1) **the mutation is scoped to a fixture nothing else asserts a fixed value against** — `admin-pos.spec.ts`'s cash-payment tests hit `DEMO_POS_TENANT_EMAIL` specifically, never the past-due tenant the portal suites depend on, and the deposit-slip test takes its own payment rather than counting on a previous test's — or (2) **the action is genuinely idempotent per day, and the spec self-skips rather than fails once it detects that state** — `admin-tasks.spec.ts`'s returned-mail flow checks whether the flag button or the task card is already in the post-action state before asserting, with `test.skip(..., 'see the note above')` and a comment naming why. `e2e/global-setup.ts` is the third leg, but only for genuinely disposable state: it unconditionally expires every checkout lock and reservation hold at the start of a run, which is safe because nothing in the suite reads a pre-existing hold. A new e2e spec against shared demo data has to fit one of these three, not invent a fourth — an unscoped mutation with no self-skip is what turns "flaky" into a description of a real bug.
