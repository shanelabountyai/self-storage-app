| D-22 | How receipt numbers are made gapless (raised during B-039, 2026-08-05) | **A `ReceiptCounter` row per facility, incremented by `INSERT … ON CONFLICT DO UPDATE … RETURNING` inside the same transaction that writes the payment.** Not a Postgres sequence, not `@default(autoincrement())`, not `MAX(receiptNumber) + 1`. Only counter-taken payments get a number; the online Stripe path leaves it null. | US-32 requires receipt numbering to be **gapless**, which is a strictly stronger guarantee than unique. A sequence does not roll back — an aborted transaction burns its number and leaves a hole no one can explain to an auditor, which is the exact failure the requirement exists to prevent. The `UPDATE` takes a row lock that serialises concurrent counter staff, and because the increment lives in the payment's own transaction, a rollback returns the number to the pool. `MAX + 1` was rejected for the opposite reason: it is not safe under concurrency without an explicit table lock, which is heavier and easier to get wrong. **Do not "simplify" this into a sequence or an autoincrement column** — both look tidier and both break the only property that matters. Tests assert all three behaviours (starts at 1 per facility, no hole after a rollback, five concurrent payments get consecutive numbers). Online card payments are deliberately excluded rather than numbered: a receipt book with holes where the web rentals were is not gapless, just confusing. |

| D-28 | How an autopay charge is tied to the invoice it pays, and when that link is written (raised during B-045, 2026-08-05) | **A charge that settles exactly one invoice names it, and its `PaymentAllocation` is written in the same transaction as the pending `Payment` row — BEFORE Stripe is called.** The webhook then recomputes `Invoice.amountPaidCents` as the sum of allocations on **succeeded** payments and sets the status from it. `Invoice.amountPaidCents` is never incremented. | The whole "autopay never double-charges" guarantee rests on the invoice reading as paid afterwards — without settlement the charge would succeed, post to the ledger, and leave the invoice open for the next night's run to charge again. **Writing the allocation before the Stripe call is the load-bearing part:** if Stripe charges the card and the process dies before the webhook lands, the allocation already exists, so the next run sees an attempt in flight and skips rather than charging a second time. None of them stops us *taking*. An automatic stay under Chapter 7 makes a charge against a debtor a violation, and charging a dead person's card is its own problem; halting the chasing while continuing to help ourselves to the balance on the same lease would be the worst of both, and would look deliberate. Deliberately NOT carried by `dispute` — a disagreement about one charge is not a reason to stop taking a payment the tenant chose to make — nor by `do_not_contact`, which is a channel instruction rather than forbearance. **Subject to the same attorney pass US-42's own note demands** (D-10): the mechanism is built now because the exposure is uncapped while it does not exist, and which effects each type must carry in Texas is a legal question this project has not answered. |
| D-32 | Which URL a facility page lives at, where two PRDs disagree (raised during B-066, 2026-08-07) | **`/storage/{state}/{city}/{facility-slug}` stays.** PRD 04 US-1 AC1's `/storage-units/…` is superseded by this entry. | PRD 01 US-103 and PRD 04 US-1 AC1 specify different paths for the same page, and neither argues for its choice. `/storage/…` is what B-016 shipped, what the search page links, what the sitemap lists and what has been indexable since. Changing it would mean a site-wide 301 and a re-crawl to buy nothing a renter or a crawler can perceive — and the shorter form reads better in a result. **The 301 map built in B-066 exists for facilities that move, not for this**; if the scheme ever does need to change, that map is what makes it survivable rather than a traffic event. |
