| D-19 | Lighthouse performance gate vs the Core Web Vitals target (raised by B-016, 2026-07-31) | **They are two different numbers with two different jobs.** The **field** target stays LCP ≤2.5s (master §7.3, PRD 01 FR-9.1) — that is the Core Web Vitals threshold real users are measured against. The **lab** gate in CI warns at 2500ms and errors at 3000ms, with run aggregation pinned. | Lighthouse's mobile lab run applies simulated 4× CPU throttling and reports pessimistically **by design**; B-016's facility page reproduced 2612/2613/2613ms on a text-only LCP element with no image and no third party left to defer, and passed only because the default aggregation picked the most favourable run — a gate that is flaky rather than green. Warn-at-2500 keeps the signal; error-at-3000 keeps the gate meaningful. **Do not "tighten" the lab error threshold back to 2500 to match the field target** — they are not the same measurement, and a later session doing so would be reintroducing a known-flaky gate. The `lighthouserc.json` change is the owner's; this log holds the reasoning. |
| D-20 | Where autopay lives, and what re-auth guards (raised during B-036, 2026-08-04) | **Autopay is a per-lease flag (`Lease.autopayEnabled`); the card it charges is a per-tenant fact (`Tenant.stripeDefaultPaymentMethodId`). Both are required — either one missing means nothing is charged.** Re-auth (US-701) gates starting or redirecting money — adding a card, changing which card is charged, removing a card, switching autopay **on** — and deliberately **not** switching autopay **off**. | Autopay had no storage at all before this: "on" was inferred from the tenant merely having a saved card, which was wrong in both directions — a renter who opted out at checkout still read as On, and one who opted in read as Off, because `provisionMoveIn` never read the choice the checkout session had recorded. Per-lease because billing runs per lease (B-045), the dashboard already reports it per unit, and a tenant with two units can reasonably want one enrolled and one not. **B-045 must read both halves**, and must treat `autopayEnabled` with no default method as a configuration error to surface, not a charge to skip silently — the portal already warns the tenant about exactly that state. The re-auth asymmetry is the part most likely to be "tidied up" later by someone making the gate uniform: requiring a fresh login to **stop** a recurring charge is the one direction where the gate does harm, because a tenant locked out of their own account would keep being billed. Enabling is gated; disabling never is. |
| D-21 | The address of record, and what the `Tenant` address columns are now (raised during B-037, 2026-08-05) | **`TenantAddress` is append-only and authoritative; `Tenant.addressLine1`/`city`/`state`/`postalCode`/`country` are a cache of the newest row, written in the same transaction.** Every address change anywhere goes through `recordAddressChange()` — portal now, counter at B-038, returned mail after that. Each row stores the address as of that moment plus source and actor; the previous row IS the old value. | US-13 requires the current address to be "derived from the latest row, never overwritten", and the reason is evidentiary: on day 40 of a lien cycle "which address did the notice go to" has to be answerable from records. A pure derivation would have meant rewriting every existing reader (lease template, comms context, admin screens) in this item, so the columns stay as a cache instead — **but a path that writes them directly leaves the history with a gap exactly where a dispute looks.** Storing an old/new pair per row was rejected: the previous row already is the old value, and holding it twice creates two things that can disagree about one fact. Existing tenants were backfilled with an `import` row in the migration, so "newest row" is true from the first read rather than only for tenants who later edit. B-038 and B-061 both depend on this being complete. |
