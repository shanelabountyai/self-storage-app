| D-22 | How receipt numbers are made gapless (raised during B-039, 2026-08-05) | **A `ReceiptCounter` row per facility, incremented by `INSERT … ON CONFLICT DO UPDATE … RETURNING` inside the same transaction that writes the payment.** Not a Postgres sequence, not `@default(autoincrement())`, not `MAX(receiptNumber) + 1`. Only counter-taken payments get a number; the online Stripe path leaves it null. | US-32 requires receipt numbering to be **gapless**, which is a strictly stronger guarantee than unique. A sequence does not roll back — an aborted transaction burns its number and leaves a hole no one can explain to an auditor, which is the exact failure the requirement exists to prevent. The `UPDATE` takes a row lock that serialises concurrent counter staff, and because the increment lives in the payment's own transaction, a rollback returns the number to the pool. `MAX + 1` was rejected for the opposite reason: it is not safe under concurrency without an explicit table lock, which is heavier and easier to get wrong. **Do not "simplify" this into a sequence or an autoincrement column** — both look tidier and both break the only property that matters. Tests assert all three behaviours (starts at 1 per facility, no hole after a rollback, five concurrent payments get consecutive numbers). Online card payments are deliberately excluded rather than numbered: a receipt book with holes where the web rentals were is not gapless, just confusing. |
