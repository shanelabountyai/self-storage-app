### B-180 — One email field for the whole quote table, and a confirmation that names the size

`f13465a`

**What it built.** The lead screen's waitlist capture rendered an email input **per size row**, labelled by nothing but a placeholder reading "Email" — which disappears the moment anything is typed, is unavailable to speech input, and asked a caller who wanted a 10x10 *and* a 10x20 for the same address twice. There is now one labelled field above the quote table, and each full size's **Join waitlist** button submits it. The confirmation names the size and the address it recorded instead of "On the waitlist."

**What it decided.**

**The per-row field was deleted, not relabelled.** Six visible labels reading "Email for waitlist alerts" down one column is a worse screen than the placeholder was, and the finding's real complaint — typed once per size — survives any amount of labelling. One field above the table is the fix; the labels follow from there.

**The buttons reach the form through the native `form=` owner attribute.** The email field lives in an `AdminForm` above the table and every "Join waitlist" button lives in a row, carrying its own `unitTypeId` as `name`/`value` on the submitter. No client component holds the address in state and no hidden input is mirrored into six forms. **This is why `AdminForm` gained an `id` prop and why the prop is not decoration:** React's `createFormDataWithSubmitter` copies the submitter's name and value into the submission by inserting a temporary input beside the submitter and tagging it `form="<id>"` — with no id on the form, that temp input is not owned by it, and every button still renders, still submits, and carries **no size at all**. That failure is silent, which is what the e2e spec exists to catch.

**`joinWaitlist` returns what the confirmation says.** The ok branch now carries `unitTypeName` and the **normalised** email, so "Added to the waitlist for the 10x20. We'll email ada@example.com…" reports what was recorded rather than echoing the box — an address typed as `ADA@Example.com` is stored, and confirmed, lowercased. The public form's copy is untouched: it deliberately gives the same words whether the visitor was already on the list or not, because that distinction is ours and not theirs.

**The success sentence says what a waitlist is not.** "…as soon as one is free — it is not a hold, and the first to complete a rental gets it." D-87's honest-copy obligation at the counter: a staffer reading "Added" to a caller must not leave them believing a unit is set aside.

**The empty-size case is refused by name.** The email field is `required`, so native validation covers an empty address across the form boundary. What it does not cover is a submission with no submitter — implicit submission from the field itself — so the action refuses an empty `unitTypeId` with "Press 'Join waitlist' on the row for the size they want" rather than passing it to `joinWaitlist`, which would report "That unit is no longer listed" and send a staffer looking for a delisted size.

**Test verification.** Full unit suite **3,724 passed, 8 skipped of 3,732** (221 files passed, 1 skipped), exit 0. Production build (via the e2e `webServer`), typecheck (including `tsconfig.tests.json`), lint and `prisma migrate diff --exit-code` clean. New `e2e/admin-leads.spec.ts`: an axe pass on the lead screen, and the wiring check — fill the one field, press one row's button, and assert the message names that row's size and that address. Run twice, 6 passed both times; the waitlist address is **fixed rather than unique per run** so the second sweep takes `joinWaitlist`'s idempotent "already on" branch (whose sentence names the same two things) instead of leaving a second row behind, which is B-120's discipline (2). `tests/inquiries-db.test.ts` asserts the returned name and email match what was recorded.

**Real bug found, not fixed here.** The full sweep failed once, on `comms-observability-db.test.ts > alertOwner > emails the owner and records the send`, expecting its own owner and getting `owner-case-…@example.com` — another suite's fixture. `ownerEmail()` in `apps/web/lib/comms/alerts.ts` is a `findFirst` for **any** active owner with no ordering, so under a parallel run it can resolve to a concurrent suite's owner. It passed alone and passed on the re-run, and the database held zero leftover `owner-*` rows afterwards, so this is a live race between suites rather than accumulation — a sibling of what **B-185** owns, and worth naming there.

**Left behind.** **The success message renders above the table.** It is inside the one form, which is above the quote list, so a staffer who pressed a button at the bottom of a six-size table hears it (`role="status"`) before they see it. B-170's page-level announce region is the mechanism if that proves to matter; it is not obviously better here, since the message would still be nowhere near the button. **The spec's "e.g. IMG_4471" placeholder has no counterpart on this screen** — it belonged to the task-form half of the finding, which is B-170's, and an email field prefilled with the lead's own address needs no example. **The e2e depends on the demo seed's `5x15 Climate` having no units** to have a full size to wait for, and self-skips with a named reason rather than failing if that ever changes.

### B-185 — The unit test database accumulates fixtures until the sweep stops being trustworthy

`68ce711a166a8990850caaafaad23e325006c769`

**What it built.** `storage_test` held 13,106 facilities and 8,276 units, all created in August 2026, none by design — only 28 of 106 `*-db` suites currently call `facility.deleteMany`, so the rest leave fixtures behind on every run. The row's own two ideas for fixing this — a shared `afterAll` cleanup helper, or a truncate-between-files hook — were tried in that order and both turned out to be impossible, not just undesirable. `audit_log`'s append-only migration (`20260730174727_audit_log_append_only`) gives it a RESTRICT foreign key to `facility` and `staff_user`, and a statement-level trigger that raises on UPDATE, DELETE, *and* TRUNCATE against itself — "deliberately no in-band escape hatch," per that migration's own comment. Building the truncate hook first and running it proved this directly: `TRUNCATE facility CASCADE` forces Postgres to also truncate `audit_log` (CASCADE follows every incoming foreign key regardless of RESTRICT), and the trigger refuses with `audit_log is append-only: TRUNCATE is not permitted`. Any fixture a suite ever audit-logged against — leases, tenant edits, impersonation, most real admin actions — is therefore permanently unwipeable by row-level cleanup, however disciplined the suite is; `access-service-db.test.ts` already carries a comment naming exactly this ("Not the facility: revealCode's audit entries hold a Restrict FK to it"). So per-suite discipline can only ever reclaim what `audit_log` hasn't pinned, which is not the accumulation this row measured.

**What actually shipped: `npm run db:reset-test`.** `scripts/reset-test-schema.mts` drops and rebuilds the `storage_test` schema in one command — the same "drop and re-migrate" recipe that already fixed the 2026-08-24 incident, now a real script instead of the "local command nobody is told to run" the row named as the actual problem. It reuses `db:migrate:test`'s own schema-create + migrate + seed logic rather than duplicating it. Deliberately not wired into `npm test`: replaying ~30 migrations against a remote Neon database on every run is the same cost `db:migrate:test`'s own comment already rules out for that reason. Verified end-to-end: dropped the schema, ran it, confirmed migrations reapplied and roles/permissions/comms reference data reseeded (`Seeded 7 roles, 35 permissions, 100 grants. Seeded 40 org-default templates, 33 org-default rules.`).

**A second, unrelated bug found in the same investigation, found while building B-180 (2026-08-25), got its own fix.** `ownerEmail()` in `apps/web/lib/comms/alerts.ts` was an unordered `findFirst` for any active 'owner'-role staff user — fine in production (there is only ever one), but a genuine race in a shared test schema, where at least 11 DB suites bootstrap their own transient 'owner' concurrently. `alertOwner`/`ownerEmail` now take an optional `Prisma.StaffUserWhereInput` (`ownerWhere`) narrowing which staff row counts as "the" owner; all four production call sites (three in `comms/detectors.ts`, one in `jobs/registry.ts`) omit it and are unaffected — only `comms-observability-db.test.ts` passes one, scoped to its own fixture's email. **Caught mid-fix, not in review:** the first version hoisted `const ownerWhere = { email: ownerEmail }` to the `describe` body, which runs during collection — before `beforeAll` sets `ownerEmail` — so it froze on the empty string and both `alertOwner` tests failed with `sent: false`. **What it built.** Three defects in one function, and it was the function the whole feature rested on. `paidSincePlanStart` summed `LedgerEntry` where `type: 'payment'` and `occurredAt >= plan.createdAt`, and that sum WAS progress — `installmentViews` allocated it oldest-first, `isFullyPaid` closed the plan, and `payment-plan-breach.ts` lifted the hold on the strength of it. **Reading the invoices is what makes the three fixes fall out rather than be built.** (1) **A returned payment no longer stays counted.** `returnPayment` posts a positive `adjustment` and deliberately leaves the original `payment` row standing (its own comment says why), and `refundPayment` posts a `refund` — but both unwind their `PaymentAllocation` rows, and `recomputeInvoices` re-opens the invoice off the back of that. So progress goes backwards without the arithmetic knowing a reversal happened, and a plan can no longer complete itself and lift its own hold on money the bank took back. (2) **Ordinary rent no longer satisfies the arrears**: a rent invoice raised after the plan started is not in the covered set at all. (3) **The plan is checked against what is owed.** `createPaymentPlan` previously computed `totalCents` as the sum of the installments and handed BOTH to `validateSchedule(installments, totalCents, now)`, so the `sum !== totalCents` branch was unreachable from the only production caller and a $50 plan against an $1,800 arrear validated, halted the ladder and completed. `totalCents` is now the lease's actual arrears, which makes that branch live for the first time — no code removed, a referent supplied.

**The derivation stays derived** (D-65, B-090c): no stored per-installment paid flag, no stored progress figure. What changed is what is summed, not where it lives. The nightly breach job recomputes from the covered invoices every run rather than accumulating, so a plan whose progress goes backwards is re-evaluated **that night** rather than at the next installment date, and an installment covered by money since taken back returns to `missed`. Clamped at zero because outstanding can legitimately exceed the frozen total — a payment that part-settled one of these invoices *before* the plan was agreed can bounce afterwards — and a negative figure would read as a credit.

**What it decided. D-96 is resolved: rent first, then the plan.** An installment is satisfied only by money that settles the arrears the plan was agreed over; current rent stays due on its own date on top. **Not per-facility configurable**, deliberately — a rule a tenant can be told only after looking up their site is a rule staff will state wrongly. The two alternatives and why each was refused are in the decision log; the short version is that "any payment counts" lets a plan complete having collected nothing toward the arrears while the tenant sits permanently behind a hold owing more each month, and "any payment minus the month's rent" reaches the same answer from cash while getting none of the reversal netting for free. **The frozen invoice LIST rather than a live `dueDate <= createdAt` filter** is the other decision worth not reversing: a fee invoice raised later the same day carries that day's due date and would silently join the covered set, making progress fall for a charge the plan never promised to clear.

**Controls and copy in the same item, because the rule is now real and a tenant is held to it.** The staff builder states the figure the installments must add up to (`{arrears} is past due on this lease`) instead of leaving a staffer to infer it from the balance beside it — `TenantLeaseSummary` gained `arrearsCents`, which is a smaller figure than `balanceCents` whenever this month's rent is invoiced and not yet due — and says in as many words that paying next month's rent does not count towards an installment. `/portal/payment-plan`'s intro said **"Paying keeps you on track"**, which was true of the code and is now false of the plan; it now tells the tenant that the plan covers what was already overdue and that regular rent is still due on top (D-15, their words). `validateSchedule`'s mismatch message moved from cents to dollars — it said `"5000 cents against 6000 cents"` for as long as it was unreachable, and a staffer reads it on a form. The `totalCents <= 0` case returns its problem **alone** rather than alongside a sum mismatch: "nothing is past due" and "your installments total $300 against $0 past due" are the same fact said twice, and the second reads as arithmetic advice on a plan that should not exist.

**Test verification.** Typecheck (including `tsconfig.tests.json`) clean; lint clean (7 pre-existing warnings, unrelated). `tests/payment-plans.test.ts` — 18 pure cases, two new: the mismatch refusal naming both figures in dollars, and the nothing-past-due refusal returning that problem and nothing else. `tests/payment-plans-db.test.ts` — 16 DB cases against real invoices and real allocations, four of them new and each pinning one defect: a plan that does not cover the arrears is refused naming the shortfall (and the same lease succeeds the moment the installments add up); a lease with nothing past due is refused; the covered invoices are frozen on the row; **next month's rent paid in full leaves installment 1 `missed` and the nightly job breaks the plan** rather than leaving the ladder halted on a payment that never touched the arrears; **a payment run back through the real `returnPayment` takes its progress back and breaks the plan that night**; and a plan whose money came back before the nightly run does **not** complete, with the hold staying on. Run twice against the un-reseeded database, both green. Full unit suite **3,786 passed, 8 skipped of 3,794** (225 files passed, 1 skipped), exit 0. Schema-drift check clean (`No difference detected`). e2e `admin-tenants.spec.ts` + `portal.spec.ts`: **160 passed, 6 failed**, all 6 `mobile-chrome`-only (`the tenant ledger`'s two, `lien notices for a lease`'s four) — the same six the B-086 entry above records, confirmed pre-existing again here by stashing this row's whole diff and re-running against unmodified `main`: identical six, identical names. The disclosure-open a11y scan of the plan builder passed on both viewports with the new copy.

**One fixture defect found in this row's own tests and fixed rather than worked around.** The suite's `pay()` helper posted a bare `payment` ledger entry, which under the new derivation moves nothing — so it had to settle an invoice through the real `applyPayment`. The first version passed no `explicitInvoiceId`, and three tests failed in ways that looked like the feature was broken. The cause is that **allocation claims run per tenant × FACILITY, not per lease**, and every lease in that file belongs to one tenant at one facility: an unnamed payment settled whichever test's arrears happened to be oldest. Every assertion in the file would have been an assertion about test ordering. `pay()` now names this lease's own oldest unpaid invoice unless told otherwise, with the reason written into the helper.

**The public accessibility statement was re-read and needs no edit**, checked rather than assumed. No new route and no new control: the two screens touched are both already in the scan lists, and the change is copy plus one emphasized figure that is also plainly stated in text. The statement's claim that a rejection is tied to its field is already false for this builder — that is **B-192 finding (3)**, and this row does not make it worse: the two refusals it adds are genuinely schedule-level rather than field-level, and a page-level message is their correct presentation. `LAST_REVIEWED` does not move.

**Left behind.** **A plan that completes and only then has its money returned is not re-opened.** Completion lifts the hold, so collections resume anyway and D-92's reversal handling takes over with its ten days of grace — the residual harm is a plan record labelled `completed` rather than an uncollected debt, and re-opening it would need a status transition and a hold nobody has asked for. Worth a row only if the label turns out to mislead someone. **An invoice VOIDED after the plan started counts as progress** — a waived fee inside the covered set reduces outstanding, so the tenant gets credit toward an installment for money nobody collected. Deliberate: the debt genuinely came down and a manager decided so. **Nothing caps what may be deferred and nothing carries a replacement plan's predecessor forward** — B-190, unchanged by this row, and its `paidSincePlanStart`-resets-to-zero symptom is now a `totalCents`-and-`invoiceIds`-reset-to-the-current-arrears symptom instead. **Autopay still does not know a plan exists in either direction** (B-189). **The tenant is still told nothing when a plan breaks** (B-191). The **remaining-balance column** both schedule tables want is B-192's and B-193's, not added here.

### B-189 — Autopay did not know a payment plan existed, in either direction

`733d444`

**What it built.** Two halves of one defect, both in the money path. **The arrears half:** `packages/core/holds/catalog.ts` gives the `payment_plan` hold `halt_dunning`, `halt_late_fees` and `halt_access_suspension` — not `halt_autopay`, the only effect `runAutopay` checks — so autopay selected every `open`/`partially_paid` invoice with `dueDate <= businessDate` and charged the **full outstanding**, on the retry ladder, for as long as the card authorised. A tenant who agreed to clear $1,800 over six months had their card taken for $1,800 the same night the plan was agreed. **The installment half:** an installment due date was a date on which nothing was charged at all, so a tenant with a saved card had to remember to pay by hand or the hour-4 breach job broke their plan for them.

**The fix for the first half is deliberately not `halt_autopay`.** That effect is all-or-nothing per lease, so declaring it would have stopped collecting current rent too and turned forbearance on what is owed into a rent holiday nobody agreed to. `runAutopay` instead skips exactly the invoices the plan froze into `invoiceIds` at creation (D-96) and charges everything invoiced since on its own due date — reported as its own skip reason (`deferred under an agreed payment plan`) rather than folded into `lease_on_hold`, because the two are different facts on the Billing Runs screen.

**An installment is one charge, not one per covered invoice.** It carries the plan id to Stripe as metadata; the webhook resolves the plan — checking its lease against the payment's own tenant and facility first, the same caution B-045's named invoice already takes — and `applyPayment` narrows the allocation to the covered set, so the money lands on the arrears in the facility's own order and can never drift onto rent the plan never deferred. Two card charges for one agreed payment is how a tenant already in collections reads their statement as a mistake, and a disputed charge is what B-147 had to build handling for. The amount is the **cumulative schedule through that installment less what the plan has retired**, not the face value: `installmentViews` reports partial coverage as uncovered, so the face value would take the same money twice.

**A declined installment is a decline, not a breach (CN-6).** `Payment` gained a nullable `paymentPlanInstallmentId` (additive migration `20260826222437_b189_payment_plan_auto_collect`), and it exists because the ladder has to be countable: an installment charge names no single invoice, so it writes no `PaymentAllocation` until it succeeds and B-045's `declineHistory` — which counts failed allocations per invoice — can see nothing at all. With it, `retryDecision` runs anchored on the **installment's own due date** (never an invoice's, never the last attempt), and `evaluatePaymentPlanBreaches` leaves the plan standing while that ladder is still running. The grace is bounded three ways so that "wait for the retries" can never become "never break": it is the facility's own `paymentRetryDays` rather than a number invented in the breach job, a terminal decline code ends it immediately, and it applies only where collection is genuinely in play.

**What it decided. D-97 is resolved: auto-collect by default, with an opt-out at agreement.** Auto-collection collects more and is kinder to the tenant who wants it handled, which is most of them; but the manual-pay argument is real — "you kept to the plan" should be able to be a statement about the tenant rather than about their card — and a checkbox costs one column and one field, which is cheaper than being wrong for every tenant in either direction. The box is ticked because that is what most plans want. **Three separate things make a plan manual-pay in fact and screens must not conflate them**: the box unticked, autopay off on the lease, or no saved card. `PaymentPlanView` therefore reports both `autoCollect` and `autoCollectEffective`, and every screen states the effective one — a plan agreed as automatic against a card since removed will collect nothing, and telling someone their payment is taken care of when it is not is how they end up in collections believing they kept to the plan.

**The control shipped with the column**, per this repo's own rule. The checkbox is on the agreement form beside the schedule rather than in a settings screen, because it is a term of the conversation being had at that moment; the action reads presence rather than a value, since an unchecked checkbox posts nothing. Both the staff plan card and `/portal/payment-plan` state in words which kind of plan it is, and the builder's existing copy now says that rent invoiced from here on is **still collected** on its own due date rather than only that it is still due.

**Test verification.** Typecheck (including `tsconfig.tests.json`) clean; lint clean (7 pre-existing warnings, unrelated). New `tests/payment-plan-autopay-db.test.ts` — 9 DB cases: the arrears deferred while September's rent is still charged; one installment charged on its due date naming the plan and **not** an invoice; nothing charged on a manual-pay plan *and* nothing swept up by the ordinary path either; only the $50 remaining of a $300 installment the tenant part-paid; no second charge while the first is still `pending`; a `card_declined` leaving the plan `active` on the first night it reads `missed` and breaking it once the schedule's last offset has passed; an `expired_card` breaking it at once; a manual-pay plan breaking the same night it always did; and an installment payment landing entirely on the covered arrears with the later rent invoice untouched. Run twice against the un-reseeded database, both green. Full unit suite **3,795 passed, 8 skipped of 3,803** (226 files passed, 1 skipped), exit 0. Schema-drift check clean (`No difference detected`). Production build clean.

**One test defect found and fixed rather than shipped.** The two breach tests first asserted on the installment's own due date, and both passed for a reason that had nothing to do with the ladder: `installmentViews` marks an installment `missed` only when its due date is strictly in the past, so on the due date itself nothing can break a plan regardless of what the card did. The terminal-decline case failed, which is what surfaced it; the "ladder still running" case had been passing green while testing nothing. Both now evaluate on the first night the installment genuinely reads `missed`.

**The public accessibility statement was re-read and needs no edit**, checked rather than assumed. The item ships no new customer-facing route: what it adds to `/portal/payment-plan` is one sentence, rendered only for a tenant with an active plan — the exact state `STATE_EXCEPTIONS` already names as unscanned, for the reason it already gives (no demo `PaymentPlan` exists). So the coverage claim goes false in neither direction. The seed row that would close that exception is B-196's. `LAST_REVIEWED` does not move.

**Left behind.** **The tenant is told none of this** — not that a plan was agreed, not that an installment is about to be charged, not that a charge declined, not that the plan broke. That is B-191's CN-24 in full, and this row deliberately does not invent a message ahead of it; the only tenant-facing change here is the sentence saying whether the card will be charged. **A declined installment raises no staff task of its own** — the Billing Runs screen records it, and a person is reached when the ladder is exhausted and the plan breaks, which raises `payment_plan_broken`. Whether the earlier signal is worth a task is a real question and belongs with B-191's comms rather than being guessed here. **Nothing caps what a plan may defer or how many a lease may have** (B-190, D-98 still open), and a chain of plans still reads on every screen as one. **The ladder's grace is measured from the facility's retry schedule, not from attempts actually made**, so a plan whose charge never fires at all — a Stripe outage, a `pending` payment that never resolves — holds open for the length of that schedule and then breaks. The bound is what makes it safe; the reconciliation report is what surfaces the stuck payment. **No report can still say who is on a plan** (B-195). **The autopay run's `payment.failed` event is not emitted for an installment decline**, because its payload is invoice-shaped; B-050's retry reminders therefore do not fire for one, which is the same gap B-191 closes properly.

### B-190 — Nothing capped what a payment plan could defer, or how many times a lease could defer it

`b4f2ee0`

**What it built.** Two holes with one shape, and D-98 answered to close them. **(1) There was no monetary authority anywhere.** `createPaymentPlan` gated on `delinquency:execute_step` and nothing else — no `checkMonetaryAuthority` call existed in the file — so a manager whose fee-waiver limit is $50 could commit the business to deferring any balance over any schedule. **(2) Nothing capped the chain.** A second plan was refused only while one was `active`, so a plan broken last night was replaceable this morning, indefinitely; each replacement re-halted dunning, late fees and access suspension, and the lien clock never ran.

Now: the deferral passes `checkMonetaryAuthority(actor, 'payment_plan', arrears, facilityId)` against a new per-role `maxPlanDeferralCents`, escalating by naming the role that can carry it. A facility configures `planMaxDays` (90), `planMaxPerRollingYear` (2) and `planGraceDays` (3), each with a control on `/admin/settings` in this item. The second plan inside the rolling year is agreed a rank up; the one past the limit is refused with the count named. `paymentPlansForLease` returns the whole chain, each plan carrying `collectedCents`, and the tenant profile states the count and the total in a sentence. Additive migration `20260827051029_b190_payment_plan_limits`.

**What it decided. The authority could not reuse the fee-waiver limit, and that is the one thing the backlog row got wrong.** B-167 settled that a departure from the fee schedule needs authority in either direction, and the row reasoned by analogy from it. The analogy does not hold: a fee waiver in either direction is a **gift**, so the limits are sized for gifts — $50 for a manager, $250 for a regional. A plan defers the **whole arrears**, typically $1,800, and gives nothing away; the money is still owed and the tenant is still on the hook for all of it. Measured against the waiver limit, every real plan on the property would have escalated to the owner, and a gate that fires on every attempt is a gate somebody switches off inside a week. So `maxPlanDeferralCents` is its own column: $0 counter and bookkeeper, $2,000 manager, $10,000 regional, unlimited owner.

**`undefined` is not `null` in a limit, and the difference is the owner's authority.** Making the new field optional on `MonetaryLimits` — so the fifty-odd test fixtures that build a `limits` object by hand did not all have to change — put a `?? 0` within reach that would have collapsed the two: `null` means unlimited by design, and `null ?? 0` caps every owner at zero on **all four** actions. It reads as an equivalent tidy-up and it is a portfolio-wide authority failure. The check is explicitly `=== undefined`, with the reason written above it and a test that deletes the field from a fixture and asserts zero rather than unlimited.

**The escalation floor is read from the role table, not compared against `manager`.** `lowestRankWith('delinquency:execute_step')` is what "a level up" means, so a role inserted between the existing two slots into the ladder without a code change — the rule `nextApproverRole` already follows.

**D-98's grace is a separate window from B-189's retry ladder and is never netted against it.** The ladder asks whether a charge is still coming; the grace asks whether the **tenant** still has time to pay some other way. So a terminal decline ends the ladder immediately and still gets its three days, and a manual-pay plan — which has no ladder at all and used to break at 00:01 over money handed across the counter that afternoon — now gets the window that was the whole point of the question. It is applied by moving the breach clock back rather than by filtering the result, so it lands identically on every path, and deliberately **not** applied to `isFullyPaid`, which has no date in it.

**Carry-forward needed no column and no arithmetic.** The row asked for a replacement plan to carry forward what its predecessor collected. D-96 already measures progress as the frozen arrears less what is still outstanding on the covered invoices, so a replacement is agreed over what was **left** and its progress correctly restarts at zero — nothing was ever discarded except the record. What was missing was legibility, and that is what shipped: the chain, newest first, with `collectedCents` per plan.

**Three numbers, three controls, in the same item** — this repo's own first hard-learned rule. They sit in the billing-policy form directly under dunning, late fees and access suspension, because a plan is the thing that stops all three, and a limit on the brake belongs beside the brake. Their own `<fieldset>` with a `<legend>`, since three fields labelled with bare nouns are otherwise three unrelated fields (WCAG 1.3.1).

**Test verification.** Typecheck (including `tsconfig.tests.json`) clean. Schema-drift check clean (`No difference detected`). Six new cases: the day cap in the pure schedule test (refused, inside, and unlimited when no ceiling is passed); `payment_plan` having its own limit in `tests/rbac.test.ts` plus the `undefined`-is-not-`null` case; and four DB cases — an over-limit deferral naming `Regional Manager` from the role table, a schedule past the 90-day ceiling, the second plan escalating and the third refused with `priorCount: 2, limit: 2`, and a two-plan chain reading as a chain with the first plan's $20 still readable beside the second. Full unit suite **3,803 passed, 8 skipped of 3,811** (226 files passed, 1 skipped), exit 0, run twice against the un-reseeded database.

**Five existing tests asserted the old break-that-night behaviour and were corrected, not deleted.** Three in `payment-plans-db.test.ts` and two in `payment-plan-autopay-db.test.ts` evaluated the breach one day past the due date. What they assert is now false for a stated reason, so each moved past the grace window with a comment naming D-98, and the one whose **name** had become false — "breaks a manual-pay plan the night the installment is missed" — was renamed rather than left to mislead the next reader. Two of them now also assert the plan is still `active` inside the window, which is the behaviour the row exists to add.

**The public accessibility statement was re-read and needs no edit**, checked rather than assumed. This item ships nothing a customer touches: the two screens are `/admin/settings` and the staff tenant profile, both already in the scan lists, and the portal is untouched. The statement's claim that a refusal is tied to its field is already false for the plan builder — that is **B-192 finding (3)**, unchanged here: the three refusals this row adds are genuinely plan-level rather than field-level, so a page-level message is their correct presentation. `LAST_REVIEWED` does not move.

**Left behind.** **No approval queue for an over-limit plan** — it names who can agree it and stops, the same posture `waiveFeeInvoice` and B-167's charge control already take; inventing a third would be the wrong place to start a queue. **`maxPlanDeferralCents` has no editing surface**, because its three siblings never had one either — B-004's scope claimed "monetary authority limits config" and PRD 02 RBAC-2 asserts the limits "are not hardcoded policy", which is currently false four times over. Raised as **B-197** rather than absorbed. **The rolling year is counted from `PaymentPlan.createdAt` with no history of the facility's own limit**, so lowering `planMaxPerRollingYear` applies to plans already agreed — the same "as of now" property D-65 names, and the right one here, since the limit is about what may be agreed next. **The tenant is told nothing about any of this** (B-191), **the builder's refusals still land page-level and the section still sits where D-95 says it must not** (B-192), and **no report can say who is on a plan** (B-195).
