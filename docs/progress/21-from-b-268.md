### B-268 — the page a Spanish reservation ends on is Spanish, date included (2026-09-07, `5f60cab`)

B-267 translated the reservation form and stopped at its redirect. `/reservations` is where that redirect goes, and it is also where the cancel link in the confirmation email lands — so it is the page that says a unit is held, the page that shows when the hold ends, and the page that releases it. It imported nothing from `@/lib/i18n`.

**What it built.** Twenty-four `res.*` keys and four `err.reservation*`, across the page and its two server actions. `generateMetadata` replaces the static `metadata` export and translates the title — unlike the marketing pages B-262 deliberately left English, because this route already carries `robots: { index: false }` and there is no crawler here to keep on English.

**The row's own warning was the smaller of the two things wrong with this page.**

- **The date, which the row named.** `formatWhen` and `formatDay` hardcoded `'en-US'`, so the hold's expiry rendered "Saturday, September 12 at 5:00 PM" underneath a Spanish label — the one fact on the page with a deadline attached, in the language the reader had just said they could not read. Both now take the locale. `timeZone` was already explicit and stays that way: it is the facility's, not the server's, which is what keeps B-228's class out of this even as the tag changes.
- **The status sentence, which it did not.** `<p>This reservation is <strong>{reservation.status}</strong>. …</p>` interpolated a `ReservationStatus` enum value straight into prose. Two defects in one line: an English word inside `<html lang="es">` with no `lang` of its own (3.1.2), and — for `converted` — a sentence that was **false in both languages**. `provision.ts` sets that status when a move-in completes, `reservationByToken` returns the row regardless of status, so a renter who had just signed a lease and paid, revisiting the link in their own confirmation email, was told the unit was *"back available for anyone to take"*. One key per ended status fixes both at once, which is why the fix is three keys rather than one with a placeholder.

**A false comment is what kept that branch unread.** `reservationByToken`'s doc comment said it returns null "for one whose reservation is no longer live". It never has — the page branches on `status` on the line after it calls it, which is the whole reason the `!live` paragraph exists. The comment has said the opposite of the code since B-018, and a reader trusting it would conclude the converted branch was unreachable. Corrected in place, and it now says why the filter is deliberately absent.

**`LOCALE_TAG` moved from `lib/comms/prose.ts` to `lib/i18n`.** B-261 wrote it beside the send path's Spanish prose, which is where it was first needed and not where it belongs: every surface that formats a date, a number or a list needs `en` | `es` widened to a BCP-47 tag, and a public page reaching into the comms module to get `'es-US'` is the wrong dependency for two strings. Values are unchanged, so all thirty-five existing callers in `comms/service.ts` render character-for-character what they did.

**What it reused rather than duplicated**, which is B-267's rule and the reason it has one: `reserve.moveInDate`, `facility.footBy` and `card.perMonth` are the same words for the same things, and a second entry per label is how two surfaces drift.

**No fourth `keyedFieldError` caller**, which the handoff asked for explicitly. The only input on this page is a hidden token, so none of the five action messages hangs on a field; all five go back as the form's summary through `messages()`. `keyedFieldError` counts fields to pick its heading and would have had nothing to count.

**`res.cancelled` joins `MUST_ALSO_DIFFER`** in `tests/i18n.test.ts` — B-267's rule, third use. It is a `status: 'success'`, so the `err.` prefix that earns the untranslated-paste guard would style it red and tell somebody who succeeded that they failed; it still confirms something irreversible, which is exactly the weight the guard exists for.

**The e2e spec takes B-120's first discipline, and it is the first spec in `i18n.spec.ts` that needs any of them.** The page cannot be reached without a real hold, so this one reserves and cancels in the same test — scoped to `demo-e2e`'s `10x10 Test`, seeded at 250 units precisely so holds need not be cleaned up, and the same fixture and the same reserve-then-cancel cycle the English specs in `smoke.spec.ts` already run. The file header said "nothing here mutates shared demo state" and has been corrected rather than left one merge behind. The expiry is asserted on the Spanish weekday rather than a literal date, because the date moves with the run: no English tag produces any of those seven words and `es-US` always produces exactly one.

**`/accessibility` re-read.** No claim changed in either direction. No route is added (`/reservations?token=not-a-real-token` has been in `PUBLIC_SCAN_ROUTES` since B-090 part 1 and still names the state it actually reaches), no new axe scan is added that could make a statement understate, and the `/` | Spanish row in `STATE_EXCEPTIONS` already covers "the rest of the public site" — this page included. `LAST_REVIEWED` not bumped (D-115): no manual screen-reader pass was performed.

**What it left behind.** The **live confirmation state has never been axe-scanned**, in either language, and is not in `STATE_EXCEPTIONS`. It needs a real hold, so no fixed URL in `PUBLIC_SCAN_ROUTES` can reach it; the new spec now builds that state, so closing it is one `assertNoAxeViolations` call plus a `SCANNED_STATES` entry — but an honest entry needs `layout`, and `'reached'` means a `STATE_REACH` key built in `e2e/a11y-own-spec-routes.spec.ts`, which is a second reserve-and-cancel cycle in a second file. That is the whole of the deferral and it is not this row's shape. **B-269** (`{terms}` still English inside every Spanish sentence that quotes it) and **B-265** (the six `sendDirectEmail` callers) are unchanged and still open. B-265 is the closer sibling now: the reservation confirmation email this page's own token arrives in is one of its six.

### B-269 — a promotion's own terms, in the reader's language (2026-09-07, `e8e27dd`)

B-266 translated the sentence around a promo code's outcome and stopped at the terms it quotes, which left «Código aplicado: 50% off the first month» — a 3.1.2 Language of Parts failure inside a sentence that had just stopped being one. This is that half, and the row understated it: five surfaces read those terms, not three.

**What it built.** `describeTerms`, `withMinStay` and the package's own `formatCents` are **deleted** from `@storage/core/promotions`. `offerTerms` replaces all three and returns an `OfferTerms` union — `operator` | `free_months` | `percent_off` | `amount_off` — and `offerTermsText` / `OfferTermsText` in `apps/web/lib/promotions/terms.tsx` write the words against a dictionary. Eight `promo.terms.*` keys per locale. This is `judgeStartDate`'s shape (B-263) and `codeOutcomeMessage`'s (B-266), arrived at a third time: a pure package has no request to read a locale from, so it returns the discriminant and the numbers.

**The five surfaces, and the row named three.** Every unit-card badge on a translated facility page (the biggest — one per size, on a page that may show six), the facility page's "what you'd pay" discount line, the checkout price summary, the applied-code confirmation, and the checkout's **"currently applied" line**, which nothing had listed. **What it decided.**

Instead the operator's words are shown verbatim and marked `lang="en"` where they stand alone, which is what 3.1.2 asks for — identify the language of a part, not translate it. The assumption (overrides are typed into an admin surface D-122 keeps English, by staff at a Texas facility) is stated in the decision rather than hidden in the code.
- **The minimum stay moved from a second function call onto every variant of the type.** `withMinStay` had to be *remembered* beside `describeTerms` at each call site; B-144's comment says why that matters — an operator override wins over the generated sentence, and a condition the renter is held to (B-145 charges money on it) must not be droppable. It is now impossible to drop by forgetting a call, which is a stronger guarantee than the one it replaces.
- **Two English surfaces are deliberate and now say so in code rather than by omission.** The admin screens resolve against `dictionaryFor('en')` explicitly (D-122), and so does `amountDueToday` — its line labels are written by `provisionMoveIn` onto invoice lines and the receipt, which is the business's own record of a charge, not a display string. - **The English is character-for-character unchanged.** `formatRate` is reused rather than a new formatter, because `smoke.spec.ts` locates by these words. The `$` it hardcodes is untouched and still B-228's class — in `es-US` the figure is identical anyway, so it is a currency question rather than a language one.

### B-265 — the emails composed in code, in the reader's language (2026-09-07, `0e8f611`)

B-261 translated the rule-driven send path: an event resolves a recipient, `effectiveTemplate` picks their language, `deliverForRule` sends it. The sends that carry a secret minted in the moment — a resume token, a reservation token, a sign-in link — bypass all of it and compose their own subject and body at the call site. This is those.

**The row said six and there were nine.** The two it missed are the **waitlist** availability mail and the **broadcast**. B-269's handoff said to count the surfaces rather than believe the row, and the reason a first pass agreed with the row is worth recording: `grep` classifies a source file containing an em dash as binary under `LC_ALL=C` and silently skips it, reporting nothing. `grep -a` found two more call sites in files the first sweep had passed over. `file` calls those same files "data".

**What it built.** `DirectEmailInput.locale` is a REQUIRED field. `sendDirectEmail` wraps the HTML part in `<div lang="…">` and resolves the appended unsubscribe label through `proseFor`. Twenty-eight sentences moved into a `DirectProse` block in `lib/comms/prose.ts`, in both languages, grouped by the message they belong to rather than flattened, so "is every sentence of the reservation confirmation translated?" is answerable by looking. Four sends are now Spanish for a Spanish reader: the checkout resume link, the reservation confirmation, the sign-in and password-reset links, and both halves of the email-change flow, plus the waitlist availability mail.

**What it decided.**

- **D-130 — the locale rule is three steps and lives in one function.** `writingLocale` in `lib/i18n/server.ts`: what the recipient told us (`Tenant.preferredLocale`, or the waitlist entry's own column), then the language of the request that caused the send, then English. The middle step is the answer to the question the row existed to ask. A renter mid-checkout is anonymous (D-7) at exactly the moment the FIRST email is sent, and English "because there is no stored preference" fails precisely the person it matters to — four Spanish screens are the only statement of language they have made. D-128's "null means never told us" is what lets the blank fall through instead of asserting English.
- **The fix went into `sendDirectEmail`, not into the nine callers.** `locale` is required rather than defaulted, on the same argument the file already makes about the marketing footer: a caller that can forget it is a caller that will, and this failure is silent. It also localizes the unsubscribe label, which was hardcoded English here while `deliverForRule` had read `proseFor(recipient.locale)` since B-261.
- **`WaitlistEntry.preferredLocale` is a new nullable column, and it is the only one this item needed.** Every other direct send happens inside the request that caused it, where the cookie is still readable. The waitlist mail is sent by the hourly sweep, hours or days later, to somebody with no `Tenant` row — so a language not captured at join time is not recoverable at all. Null means "never told us", the same fact the tenant column carries; the entries already on the lists must not be recorded as having chosen English.
- **Three sends stay English by decision and now say so in code.** The platform alert and the scheduled report are staff (D-122). The **broadcast is the interesting one**: it has `recipient.locale` available and deliberately does not use it, because its body is `input.message`, free text a staffer typed — D-129's operator half. Selecting the seeded Spanish template would wrap English words in `lang="es"`, which is the exact 3.1.2 failure the new wrapper exists to prevent.
- **Staff are refused the request's cookie outright.** `requestPasswordReset` serves both audiences, so `linkLocale` returns English for a staff subject rather than resolving the browser they happen to be sitting at — otherwise an admin whose browser was left in Spanish gets a Spanish reset link.

**Two real defects found on the way, both in the email-change flow.** The tenant's own first name was interpolated raw into the HTML part of both messages, so a name containing a tag reached the inbox as a tag; every interpolated value is escaped now, through the same `escapeHtml` the render path uses. And the plaintext half of the security notice carried a SHORTER sentence than its HTML half — it dropped "it only takes effect when the link we sent to that address is opened", which is the half that tells somebody reading an alert about their own account that they still have time. One sentence renders both parts now, with the new address arriving bold in the HTML and plain in the text (`MergeValue`'s device).

**`/accessibility` re-read, and this one closes a gap rather than disclaiming one.** B-261 fixed `renderEmail`'s hardcoded `<div lang="en">` on the templated path. All nine direct sends had **no language declaration at all** — survivable only while every one of them was English, and 3.1.2 the moment four of them became Spanish. No claim on the page needed correcting in either direction: it has said nothing about email since B-198 settled that it says nothing either way, and that sentence held. The "Where we fall short" list is unchanged in scope. `LAST_REVIEWED` not bumped (D-115): no manual screen-reader pass was performed.

That is B-263/B-264's class (a form inside a translated facility page), one surface neither of them reached, and no row is open for it.
