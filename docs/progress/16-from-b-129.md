### B-129 (part) — The auction lot sheet, and the readiness check that decides what may be advertised

`1350aa8`

**What it built.** The half of US-30's advertising story that does not depend on an unanswered question. **B-129 stays open**; both of its blockers are still blockers.

`/admin/auctions/lots.csv` is a structured lot sheet — lot number, facility name and address, unit number, size and square feet, sale date, terms of sale, case reference — that an operator uploads to a marketplace, hands to an auctioneer, or reads down a phone to a newspaper. `/admin/auctions` gains an **Advertising the sale** section that offers it, and a **Not on the sheet** list. `/admin/settings/delinquency` gains a terms-of-sale form.

**What was deliberately NOT built.** No marketplace driver, no vendor API call, and no `AuctionAdvertisement` row written by exporting. Downloading a sheet is not evidence that an advertisement ran; that row stays typed by the person who placed the ad, with the publication and the tear sheet (B-062). Master PRD §11 OQ-9 — live on-site auctions versus online — is still open, and a CSV is neutral between the two in a way a driver written against one vendor's API would not be.

**What it decided.**

- **D-104: the lot sheet ships while OQ-9 stays open; the driver does not.** The row itself had already named this as the safe first move — "useful whichever way OQ-9 goes and fabricates nothing" — and the owner confirmed it rather than my inferring it from a sentence that also said "when it is unblocked". D-63's no-simulator rule is untouched, because nothing here simulates a third party: every figure on the sheet is a fact this system already holds about its own facility.
- **The selection rule is the item, not the download.** A lot is exportable only if it is `scheduled`, carries a sale date, **and still passes live `auctionReadiness`** — the same function the case screen refuses on. `status` is not the test and cannot be: a sale is scheduled once and then sits for weeks, and the tenant paying, an SCRA or bankruptcy hold landing, or a titled vehicle being recorded all leave `status` at `scheduled` while making the advertisement wrong. The database test for this pays the lien off and asserts the lot drops off the sheet **with the case row unedited** — status still `scheduled` — which is the property no amount of filtering on status could give.
- **Every dropped case is named, with its blockers.** A short CSV nobody realises is short is the failure mode; "three of your five scheduled sales are not on this sheet, and here is why" is the screen. Sold and cancelled cases are silently omitted rather than refused, because nobody is about to advertise them and a refusal line for each would be noise on a list whose whole value is being read to the end.
- **Terms of sale are a facility column with its control in the same item**, per this repo's rule, and it is its **own form** rather than a field on the timeline. Saving the timeline mints a version every governed lease stays pinned to (US-29); editing a comma in the terms of sale must not bump the version each open case's approval screen cites. Terms are current policy, a timeline version is evidence. Null stays a real state — blank column, and the auctions screen says the terms are not set — which is D-63's honest-degradation posture rather than a plausible default becoming a term nobody chose.
- **`facility:settings` was added to one test actor, not to the shared `ALL` list.** That list is used by every actor in `auctions-db.test.ts`, and widening it would quietly weaken whatever refusals the other 40 tests rely on.

**Accessibility.** Everything here is behind `auctions:approve` or `facility:settings`, so nothing a customer touches changed and the public statement gains no claim — the same reasoning as B-197, recorded on the page rather than left implicit. Both screens are already in `ADMIN_SCAN_ROUTES`, so the new markup is axe-scanned and — since B-201 — measured at 320px, at 200% zoom and under forced text spacing. The refusal list is a list of links with the reason as text beside each, so nothing is carried by colour or position.

**Test verification.** Typecheck clean including `tsconfig.tests.json`. Lint clean (7 pre-existing warnings, none in these files). Full unit suite **3,886 passed, 8 skipped of 3,894**, exit 0 — 11 new, eight on `selectListableLots` and three against real rows. `prisma migrate diff --exit-code`: **no difference**; the migration is applied to `storage_test` and to `public` (`db:migrate:test`, `db:migrate:e2e`). ### B-218 — `gh pr ready` now runs the e2e lane, which it never has

`6371f1f`

*(Recorded as `94d49de` when built. That commit, and B-202's, were squash-merged into `6371f1f` via PR #17 — the squash collapsed five commits and orphaned every SHA on the branch, which is the same defect the "record the SHA in a follow-up commit, never by amending" rule exists to prevent. Merge with `--rebase`, not `--squash`.)*

**What it built.** One line in `.github/workflows/ci.yml`: `types: [opened, synchronize, reopened, ready_for_review]` on the `pull_request` trigger.

**The bug it fixes, which was in the gate rather than in the code the gate guards.** `on: pull_request` with no `types:` defaults to `opened, synchronize, reopened`. `ready_for_review` is not one of them, so `gh pr ready` fired no workflow event at all — and the `e2e` job, guarded by `github.event.pull_request.draft == false`, kept the `skipping` conclusion it had earned on the last push, back when the PR still *was* a draft. Found by doing exactly what the repo's own "Pull requests" section says to do: marking B-206's PR ready and expecting the heavy lane to run. It did not, and `gh run list --branch` showed no run after the toggle. All sixteen open PRs report `e2e=skipping`.

**What it decided.**

- **`gh run rerun` is not a workaround and must not be offered as one.** A re-run replays the original event payload, in which `draft` is still `true`, so the guard skips the job again. The only things that have ever run e2e on this repo are a merge to `main` and a push while the PR was already non-draft — the first of which is *after* the moment the gate exists to guard.
- **The trigger is fixed rather than the job's `if`.** Loosening the guard to run e2e on drafts would restore the ~30 minutes of Actions time per draft push that splitting the lanes was built to stop spending. The defect is that the ready signal never arrived, not that the condition is wrong.
- **`paths-ignore` is untouched.** Adding `types` alongside it is additive; both filters still apply, so a docs-only push still skips both lanes.

**What it left behind.** **The sixteen PRs already open do not heal retroactively.** For a `pull_request` event GitHub reads the workflow from the PR's merge ref, so each of them picks the fix up on its *next* event — one more draft→ready toggle, or any push. Nothing re-runs on its own. **No test covers this**, and none reasonably can from inside the repo: the failure is in GitHub's event routing, and the check that would have caught it is reading the `types` default in the Actions documentation. The comment above the line is the guard against someone deleting it as noise.

### B-202 — a payment plan now blocks the auction it always should have

`6371f1f`

*(Recorded as `b06b9b5` when built; squash-merged into `6371f1f` via PR #17 — see the note on B-218.)*

**What it built.** One array element: `block_auction` added to the `payment_plan` entry in `packages/core/holds/catalog.ts`. **What it decided.**

**What it left behind.** **No new test file.** The catalog test that asserted the old behaviour (`hasEffect(payment_plan, 'block_auction')` → `false`) now uses `dispute` for its negative case, and `payment_plan` joined the loop asserting `block_auction` on every type where a sale is unrecoverable — with a comment saying it is there for a different reason than the federal ones. Every layer below the catalog is already generic over the effect and already tested that way, so a per-layer suite would test the catalog three more times. **The cancel-versus-block question is open**, as above.

**An environment note, because the first full sweep was red and none of it was this change.** 18 failures across 8 `*-db` files, 30 occurrences of `FATAL: sorry, too many clients already` in the log, and the three `AssertionError`s downstream of it (a fixture facility that never got created surfacing as `unknown_facility`). That is the shared-state trap this repo already has written down, not a defect in the code under test, and `newLeaseUnderOwnTenant` is the fix. ### B-204 — An installment charge honours `halt_autopay`

`3d6b6c4` (`--rebase` merge of PR #19 rewrote the commit; it was `40ee469` on the branch)

**What it built.** `collectInstallments` (`apps/web/lib/billing/autopay.ts`) consulted no hold at all. `runAutopay`'s invoice loop has honoured `halt_autopay` since US-42; the installment half, added by B-189 in the same file, had only three guards — `plan.autoCollect`, `lease.autopayEnabled` and a saved card. `military_scra`, `bankruptcy` and `deceased` all declare `halt_autopay` (`packages/core/holds/catalog.ts`), so a bankruptcy hold placed on the 10th did not stop the 3am charge on the 15th. That is a stay violation committed by the system *after* somebody correctly told it not to, and it is a charge against a real person's card.

The fix is the one the row prescribed: `activePlansFor` now runs before the hold read, both lease populations go into one `effectsByLease` call, and `collectInstallments` takes the resulting set and skips those leases.

**What it decided.**

- **The hold set is read over BOTH populations, and that is the load-bearing half of the fix.** An installment is charged off the PLAN, not off an invoice. A plan lease whose arrears are entirely frozen has nothing in `runAutopay`'s invoice query — nor does one whose tenant has moved out still owing the debt the plan covers, because that query scopes to `OCCUPYING_LEASE_STATUSES`. A set built from the invoice list alone therefore misses exactly the leases `collectInstallments` is about to charge. Passing the existing set through unchanged would have looked like the fix and closed only the easy half.
- **One `effectsByLease` call for both halves, not two.** The same reason `activePlansFor` is read once and shared: two reads are one reordering away from disagreeing about which leases are held, on the question of whether to take money from a bankrupt.
- **The hold check is the first test in the installment loop, ahead of the three manual-pay ones, and it records a skip rather than `continue`ing silently.** A stay, an SCRA protection or a death is not a billing preference, and a plan agreed before the hold landed does not survive it. The three manual-pay reasons pass silently because none of them is an event; this one is, so the run names the lease it stood down on and the message is the same `lease_on_hold` string the invoice loop already uses.
- **No change to the `payment_plan` hold itself.** B-189's reasoning stands: `payment_plan` deliberately does not declare `halt_autopay`, because that effect is all-or-nothing per lease and would turn forbearance on arrears into a rent holiday. This item is about the *other* holds.

**Accessibility.** Nothing a customer touches changed — no route, no markup, no message. `apps/web/app/(public)/accessibility/page.tsx` was re-read per the standing obligation; no sentence went stale in either direction and `LAST_REVIEWED` does not move.

**Test verification.** Two new tests in `tests/payment-plan-autopay-db.test.ts`: a bankruptcy stay stops the installment and the run says so, and a `deceased` hold on a plan lease with **no invoice in tonight's run** (tenant moved out; lease `ended`) is still honoured — the second is the one that fails on a fix that only passes the old set through. **Both were confirmed to fail against `main`'s `autopay.ts` and pass with the change**, rather than being assumed to cover it. Typecheck clean including `tsconfig.tests.json`. Lint exit 0 (7 pre-existing warnings, none in these files). Full unit suite **3,894 passed, 8 skipped of 3,902**, exit 0 — the two new tests are the whole delta from **3,892 passed, 8 skipped of 3,900 measured on `main`** immediately before this change. (B-205's entry above records 3,890/3,898; `main` measures two more, so that figure was written before the last of that row's own tests landed. Noted rather than corrected, since the entry's other numbers stand.) `prisma migrate diff --from-migrations --to-schema-datamodel`: **no difference**; no migration in this row.

**Left behind.** **The sibling defect the row names is B-208, not this one**: `halt_late_fees` and `halt_dunning` are still evaluated per lease rather than per invoice, so a plan still halts the fee ladder on rent it never deferred. That is a separate row with an owner number to settle first. **No backfill of charges already taken** — if a charge was collected under a stay before today, unwinding it is a refund decision a person makes, and nothing here looks for one.

### B-208 — A payment plan stops covering for rent it never deferred

`e4276e6`

**What it built.** `halt_late_fees` and `halt_dunning` are evaluated per LEASE, not per invoice (`apps/web/lib/billing/late-fees.ts:88`, `packages/core/delinquency/engine.ts:63`), so a payment plan's hold stood every collections mechanism down on the whole lease — including rent charged after the plan was agreed, which the plan never promised anything about. 1. **The nightly breach job now also breaks a plan on unpaid post-plan rent.** `overdueRentOutsidePlan` (`apps/web/lib/delinquency/payment-plan-breach.ts`) looks for a `rent` invoice on the lease that is **not** in the plan's frozen `invoiceIds`, is not `void`, still has an outstanding balance, and is past due by at least the facility's own first late-fee day. Asked only when the schedule itself is being kept — an installment breach already names the installment and needs no second reason.
2. **N is the facility's own `LateFeeRule` step 1 `daysPastDue` (D-107).** `lateFeeStepsFor` was made exported for it. 3. **A sixth payment-plan email, `payment_plan_broken_unpaid_rent`**, on a new `payment_plan.broken_unpaid_rent` event carrying `invoiceId`. It already told the tenant "Rent for each new month is separate from this plan and is still due on its usual date" — this makes the consequence explicit before it is applied.

**What it decided.**

- **No new setting, and that is the load-bearing choice (D-107).** "When is rent late here" is a question this facility has already answered, effective-dated, with a control an operator has used. A `planCurrentRentGraceDays` beside the late-fee ladder would be a second column configuring the same intent — the accumulation this repo's first rule is about — and it would drift from the ladder the moment either was edited. The coupling is also right on its own terms: a lenient ladder buys a lenient plan rule automatically. A flat constant was rejected for the reason D-10 makes compliance per-state configurable.

That is how a collections message becomes the thing a tenant is angriest about, and this repo already treats false customer-facing sentences as load-bearing (B-211's whole subject). The cost is one template, one event, one resolver.
- **`invoiceId` on the event, not re-derived at send time.** Same rule B-206 established for `installmentId`: which bill ended the plan is a decision this job made against a grace window the send path has no business re-running.
- **Rent only.** A `fee` invoice raised after the plan started should not exist — the hold is stopping the ladder that would raise it — and ending somebody's forbearance over one is not what "current rent stays due" means.
- **The frozen arrears can never trigger it.** `notIn: plan.invoiceIds` is the entire mechanism, and the first new test asserts it: at four days past the post-plan rent's due date the plan is still active with its original arrears invoice unpaid, which is exactly what a plan is for.

**Accessibility.** Nothing a customer touches on the site: a nightly job, one event, one email template — no route, no state, no control. `apps/web/app/(public)/accessibility/page.tsx` was re-read per the standing obligation and a note appended. No claim moves in either direction, and `LAST_REVIEWED` does not move. The note records why a sixth email adds no sentence: B-198 settled that this page says nothing about email in either direction, because a client's rendering of a message is not the site.

**Test verification.** Two new tests in `tests/payment-plans-db.test.ts`, both against a facility given a real `LateFeeRule` step 1 at day 5 (created per test, because every other test in that file is written against a facility with none). The first asserts the plan survives at four days past due and breaks at six, that both hold effects are gone, that the recorded message names rent rather than an installment, and that the `payment_plan.broken_unpaid_rent` event row exists. The second asserts the dangerous direction — paying that rent, named explicitly to its own invoice so it cannot settle the older frozen arrears, leaves the plan active and `halt_dunning` in force. Both were mutation-checked: stubbing `overdueRentOutsidePlan` to return null fails them. Full suite green — 3905 passed, 8 skipped, 3913 of 3913 — with no schema change, so no migration and no drift.

**What it built.** Two portal defects the UX review raised, merged because both are the same mistake: the screen states something worse than what the product actually does, to the tenant whose next move is deciding whether it is worth paying.

1. **`installmentViews` gained a fourth state, `late`, and the deadline that goes with it** (`packages/core/payment-plans/schedule.ts`). D-98 (4) gives a missed installment `planGraceDays` (default 3) before the plan breaks, and that number reached exactly one place — `evaluatePaymentPlanBreaches`, which applies it by moving its own clock back. Every other reader marked an installment `missed` the instant its date passed. The function now takes the window and returns `late` for an installment past its date but inside its grace, `missed` past it, with `graceEndsOn` on every view — the day the tenant is actually held to. `graceDays` defaults to `0`, which makes `late` unreachable and reproduces the old two-state behaviour exactly, so no caller changed meaning by being missed.
2. **Three schedules and the halted-leases report pass the facility's window through** — `paymentPlansForLease` (both portal and staff plan tables) and `haltedLeases`, where `missedCount` had been counting installments a day past due as breaches on a report an owner reads. The row renders **"Late — pay by 29 August"** on `/portal/payment-plan` and on the admin tenant profile, in words with a date in them rather than as a colour (1.4.1 A); `missed` keeps its red "Missed".
3. **The portal dashboard card tells late and missed apart** (`apps/web/lib/portal/dashboard.ts`, `apps/web/app/portal/page.tsx`). `late` is its own fact beside `next` and `missed`, carrying `payByDate`: *"A payment on your plan is late. $306.24 was due on 26 August. Your plan carries on if you pay it by 29 August."* Both the late and the missed paragraphs now link to `/portal/pay` **with the installment amount on the link**, the correction B-193 already made on the plan page — an installment schedule that quotes the whole arrears offers the tenant the figure the plan exists to replace.
4. **The card goes quiet once the lease owes nothing.** It rendered for `status === 'broken'` with no time bound and no balance test, so "Your payment plan has ended… the full balance above is due now" was permanent — printed directly under a $0.00 balance — for every tenant who broke a plan and then paid it off. It is now gated on the lease's ledger balance being positive. The plan itself stays on `/portal/payment-plan`, which is where a record of something finished belongs.
5. **Both plan emails state the rule they are about to be judged by**, through a new `plan.grace_line` merge field (`packages/db/comms-catalog.ts`, `apps/web/lib/comms/service.ts`). `payment_plan_agreed` and the installment reminder both said the plan ends the day a payment is missed — which is not what the job does, and a tenant told the plan is already gone has no reason to pay by the date that would in fact save it. The line is composed at send time from the facility's own setting, so it cannot go stale when somebody edits it.
6. **The plan builder quotes the same rule at the counter** (`apps/web/app/admin/tenants/[tenantId]/page.tsx`): "an installment still unpaid 3 days after its date lifts it automatically", not "missing an installment".

**What it decided.**

- **`late` is a state, not a shade of `missed`.** Folding it into `missed` with softer wording was the smaller diff and it loses the only thing the tenant can act on — the deadline. Telling somebody their plan has ended when it has not is the same class of harm D-97 names in the other direction (telling them a payment is taken care of when it is not): both are a reason to stop trying.
- **The breach job is unchanged, and the two must land on the identical boundary.** It still shifts its own clock rather than passing `graceDays`, because it measures B-189's retry ladder against the *unshifted* due date in the same call and the two windows must never be netted against each other (D-98 (4) says so outright). That makes boundary agreement a real risk — a plan that breaks on a night the portal says it is alive is this same defect facing the other way — so a test asserts the two agree day by day across the window rather than trusting that `dueDate + grace < asOf` and `dueDate < asOf - grace` are the same inequality.
- **The window is stated as a number, not described.** "You have a few days" is not a rule a tenant can keep. It is read fresh from the facility on every send and every render for the same reason: a sentence with "three days" typed into it goes quietly false the day an operator edits the setting.
- **Zero grace is a real configuration and gets the old sentences back**, in the emails and in the builder copy — where the plan does break that night, there is no catching up to describe.
- **The dead card is suppressed on the BALANCE, not on a time bound.** A "hide it after 30 days" rule would still be wrong on day 29 for a tenant who paid, and still lying on day 31 to one who has not. What made the sentence false is that nothing is due, and that is exactly what the test is.
- **No new decision row.** D-98 (4) already settles the number and its separateness from the retry ladder; what was missing was that anything other than one nightly job knew about it. PRD 01 §4.7 and PRD 02 US-25 carry the AC.

**Test verification.** Four unit tests on `installmentViews` (`tests/payment-plans.test.ts`): `late` inside the window with `graceEndsOn` on it, the flip to `missed` the day after the grace ends, the boundary-agreement test above across five dates, and one asserting the zero-grace default is byte-for-byte the old behaviour. `tests/portal-dashboard.test.ts` now asserts the card at one day past due (`late`, with `payByDate`, `missed` null) as well as at five (`missed`, `late` null), and that a broken plan's card disappears the moment the ledger balance reaches zero and no other plan state moved. Two existing db tests in `tests/payment-plans-db.test.ts` that asserted `missed` at +2 while breaking at +5 — with a comment calling that two separate windows, which it never was — now assert `late` at +2 and `missed` at +5, the same day the job ends the plan. Two comms tests assert the emails carry "3 days to catch it up". Full suite green: **3911 passed, 8 skipped, 3919 of 3919**. Lint, typecheck, production build and `prisma migrate diff --exit-code` clean — no schema change, so no migration.

**Accessibility.** Customer-facing, and it adds a state to two portal screens. Both new states are told apart by **words** (1.4.1 A) — "Late — pay by 29 August" is a sentence with a date in it, not an amber cell — and the dashboard card is still a server-rendered `role="status"` present at page load rather than inserted on change (4.1.3 AA). `apps/web/app/(public)/accessibility/page.tsx` was re-read per the standing obligation and a note appended; `LAST_REVIEWED` does not move, because no claim on it was re-checked against the build and none changed. **Two `STATE_EXCEPTIONS` were widened in the understating direction**: the `/portal` card exception named "the two warning states" and there are now three, and the `/portal/payment-plan` exception covered only ended plans while the late and missed ROW states of a live one had never been named at all.

**Left behind.** **Neither new state is scanned**, and that is declared rather than closed: both need an installment whose date has actually gone by, which the demo seed deliberately does not create — a past installment would be broken by the nightly job on a schedule nobody controls, so the fixture would show a different thing depending on when the jobs last ran (B-193's entry settled that). **`isBreached` in `packages/core/payment-plans/schedule.ts` still has no grace argument and no production caller** — only tests reach it — so it is correct today and would be wrong the moment somebody used it; it wants deleting, not fixing. **The halted-leases CSV and the staff plan card still say "Missed" for a count**, now a correct count, but nothing on those screens names the grace window the way the tenant's schedule does. **No SMS equivalent**: `plan.grace_line` is on the two email templates that stated the wrong rule, and the SMS catalog has no plan messages to correct.

### B-211 — Three screens described behaviour the product does not have

`fd3ea9e`

**What it built.** Copy only, no logic: three statements the product makes about itself that were false, and — for the first one — the two places the false statement came from rather than only the screen it was read on.

1. **`/admin/settings/roles` told the owner that over-limit work escalates.** The words were *"Over the limit does not fail: it escalates to the next role up that can cover the amount"*. Nothing escalates. B-190 shipped a hard refusal that **names** the lowest role above whose limit covers the amount, and there is no queue behind it: nothing is routed, nobody is notified, and the person named has to perform the action themselves. The screen now says that, and says the ordering rule is what keeps the refusal honest — a role left more generous than the one above it would send staff to somebody with *less* authority than the person just turned down.
2. **The same sentence was fixed where it originated, not only where it was read.** `ladderViolation`'s own refusal (`apps/web/lib/admin/role-limits.ts`) told an owner editing the limits that the role above "is who an over-limit fee waiver escalates to"; it now says the refusal *sends staff to* them. And the comment on `checkMonetaryAuthority` (`apps/web/lib/rbac/authorize.ts`) said over-limit "routes to the next role up… the approval workflow itself lands with refunds in **B-048**" — B-048 shipped, without it. That comment is where the screen's sentence came from, and leaving it would have re-grown the copy.
3. **`invoiceLeadDays` configures two things and its label named one.** `emitInstallmentReminders` reads it to decide how far ahead a plan-installment reminder goes out (B-191 chose it deliberately, rather than adding a second column configuring the same intent), while the control said only "Invoice this many days ahead". Shortening invoice lead time silently moved every installment reminder — on the population that most needs the warning. It now carries a hint saying so.
4. **The `plan.schedule` merge-field help described a rendering D-102 replaced.** It read "Every installment, one per line, with its date and amount", which was true until B-198 made the field a `MergeValue` — a numbered list in the text part and a captioned table in the HTML one. **The template editor prints `description` verbatim** (`/admin/settings/templates` renders it as the `<dd>` of the field list beside the box), so that sentence is the only guidance an operator gets, and an operator who wrote the field inside a sentence dropped a table into the middle of a paragraph. It now says it is a block and to keep it on its own line.
5. **PRD 02 RBAC-2 asserted the routed approval request too**, and was corrected in the same pass — it is the line the screen was faithfully implementing.

**What it decided.**

- **No new D-number.** D-98 already settled the posture — "escalation by naming the next role, the same posture as a fee waiver, **with no approval queue behind it**" — so this is the PRD and three surfaces catching up with a decision that was already recorded, not a decision being made.
- **A routed approval request stays unbuilt, and now says so out loud.** RBAC-2 has asked for one since the beginning and no backlog row owns it. Inventing the row was tempting and is product-owner work, not a copy item's; what the copy item can do is stop the product claiming the feature exists. The PRD line names the gap explicitly so the next person reading RBAC-2 sees an unbuilt requirement rather than a built one.
- **Fixed at the source, not at the symptom.** Three of the five edits are not the screen the row named. A false sentence in a doc comment beside the function is how the same false sentence gets written on the next screen.
- **`invoiceLeadDays` keeps its one number.** The alternative — a second setting for the reminder — is exactly the accumulation this repo's first rule is about, and B-191 rejected it on those grounds. The defect was never the sharing; it was that only one of the two meanings was written down.

**Test verification.** Nothing executable changed: five strings, one PRD line. No test asserted any of them (a comment in `tests/role-limits-db.test.ts` used the old word and is unchanged, being a comment). Full suite green — **3911 passed, 8 skipped, 3919 of 3919** — with lint, typecheck, production build and `prisma migrate diff --exit-code` clean. No schema change.

**Accessibility.** Nothing a customer touches: `/admin/settings/roles`, `/admin/settings`, and the merge-field list on `/admin/settings/templates` are all staff screens behind `settings:manage`. `apps/web/app/(public)/accessibility/page.tsx` was not edited and no claim on it moves in either direction. The one new element is a `hint` on an existing `Field`, which the component already wires into that input's `aria-describedby` (3.3.2 A) rather than leaving as adjacent text.

**Left behind.** **Two refusals still say "Ask a manager to approve it" with the word hardcoded** — the fee-waiver and refund paths in `apps/web/app/admin/tenants/[tenantId]/actions.ts` — while the payment-plan and fee-override refusals beside them use the data-driven `escalateTo` name and say what happens when nobody above can cover it either. On a portfolio whose roles have been renamed, or where no manager's limit reaches, "ask a manager" is the same class of false sentence this item was about; it wants the same treatment and did not get it here. **The approval queue itself has no row.** **`tenant-rate-increases.ts:237` still says "escalates to the next role that can carry it"** in a comment — accurate in its own terms, since it is describing where the refusal points, but it is the wording that produced this item and would be better said the other way.

### B-212 — The payment-plan builder is offered where it cannot work, and where it can, it demands cent-exact arithmetic across twelve fields

`14904be`

**What it built.** Two halves, both about the same form on `/admin/tenants/[tenantId]`.

**Not offering a control that cannot succeed.** The disclosure rendered for every non-ended lease with no active plan and no arrears test, so on a current tenant it opened to "$0.00 is past due" over twelve fields and refused every submit — `validateSchedule` returns *"There is nothing past due on this lease to put on a plan"* before it looks at anything else. It is now gated on `arrearsCents > 0`. The rolling-year cap was the same failure one step further in: D-98's `planMaxPerRollingYear` is checked by `createPaymentPlan` **before** the schedule, so a staffer at the limit filled in six dates and six amounts for nothing. The profile now renders that refusal in place of the form, in the server's own words including where the limit is changed.

**Doing the arithmetic the refusal demands.** Where a plan can be agreed, the builder gained an **even split** — installment count and start date, one button — and a **live "still to allocate" figure**. Up to six date/amount pairs had to sum to the arrears to the cent, by hand: $1,837.42 over six months is 5 × $306.23 + $306.27, computed in somebody's head, in front of a tenant, with nothing on screen keeping score. Both are suggestions, not constraints: every field stays editable and `validateSchedule` remains the only thing that decides whether a schedule may be agreed.

**Naming the two money figures.** The leases table's balance and the builder's past-due total are different numbers for the same lease, and a staffer who typed the first was refused with nothing saying why. The column header is now **Total balance**, and the builder says the difference in one sentence — but only when the two actually differ. The plan-chain `role="note"` now renders only at `count > 1`; a chain of one restated the card directly below it, in worse words, in a box that reads as a warning.

**What it decided.**

- **The cap count comes from ONE function, `planCapFor`, extracted from `createPaymentPlan` and exported.** A screen that recounted the plans off the cards it already has would have been two lines shorter and wrong: B-209's same-day-correction discount means the raw count over-states, so the profile would have refused plans the server would take. That is worse than the defect being fixed — a form that cannot be submitted wastes a minute; a refusal that should not exist sends a tenant away. The extraction moves the B-209 reasoning onto the shared function, where both callers read it.
- **`evenSchedule` floors every installment but the last, so the last is the largest.** Ceiling-and-shrink reads slightly better and produces a final installment of **zero** on a small arrears (20¢ over six is 4,4,4,4,4,0), which `validateSchedule` then refuses — a "fill this in for me" control that yields a refused form is the defect this row exists to fix, not a new one. The count is also clamped to the arrears in cents for the same reason.
- **Day-of-month is clamped, not rolled.** Naive month arithmetic turns 31 January into 3 March, which puts two installments in March and is refused for being out of order — a suggestion that cannot be accepted.
- **It is pure and lives in `packages/core/payment-plans`, beside the validator that refuses it.** It is arithmetic about money and is the kind of thing that should be checkable without a clock or a query, the same reason the rest of that module is there.
- **The split controls and the running total sit OUTSIDE the `<AdminForm>`.** They are a calculator, not plan data — nothing there should be posted — and `AdminForm` already owns a `role="status"`, which a second one inside the same form would make ambiguous to every `form.getByRole('status')` in the suite (B-184's comment says so at length). Scoping to the `<details>` still finds two, which is what the new spec's `.first()` and its comment are about.
- **The builder became a client component** (`apps/web/components/admin/payment-plan-builder.tsx`), the `ChargeFeeForm` pattern. A running total and a fill button need state; nothing else on that page does.
- **No new D-number.** D-98 settled the caps and B-209 settled the correction discount; this is the screen catching up with both.

**Test verification.** Four unit tests on `evenSchedule` (`tests/payment-plans.test.ts`): it adds up **exactly** at every count from 1 to 6 across five totals down to 1¢ and never emits a non-positive installment; the schedule it produces is accepted by `validateSchedule` itself; 31 January runs 31 Jan → 28 Feb → 31 Mar → 30 Apr; and the count is clamped by both the form's row ceiling and the arrears. Two new e2e tests in `e2e/admin-tenants.spec.ts` — one fills the schedule on Dana and reads the running total through to "Adds up exactly", one asserts the disclosure is absent on a lease with nothing past due (`alex.active5@demo.example.com`). **Both are read-only against the shared demo fixture** (B-120): filling a form is not a mutation, and agreeing a plan on Dana would place a `payment_plan` hold and halt collections on the one lease the dunning specs need chased. Full unit suite green: **3915 passed, 8 skipped, 3923 of 3923**. `e2e/admin-tenants.spec.ts` green on both projects, **50 passed**, twice. Lint, typecheck, production build and `prisma migrate diff --exit-code` clean — no schema change, so no migration.

**Accessibility.** Nothing a customer touches: this is `/admin/tenants/[tenantId]`, behind `delinquency:execute_step`. `apps/web/app/(public)/accessibility/page.tsx` was not edited and no claim on it moves in either direction. The two new controls are `Field`s rather than hand-rolled inputs specifically so they inherit B-201's `min-w-0` — the five local hand-copies of that class string are why that fix reached some screens and not others. The running total is a `role="status"`, so it is not sighted-only. The existing route and "payment plan builder refused" state scans both still pass.

**Left behind.** **B-213 is untouched and is the reason this row did not go further**: the per-installment refusal is on the `<fieldset>` via `aria-invalid`/`aria-describedby`, which no shipping screen reader announces, so B-192's headline fix is still visual-only — and the two new e2e tests deliberately do not submit, so the test gap B-213 names (nothing in the repo renders a per-installment `fieldError`) is still open. **The running total announces on every keystroke** in principle; polite regions coalesce, so in practice it announces once the typing stops, but it has not been watched with a screen reader and this repo does not assert AT behaviour nobody has watched. **The even split is monthly only** — no fortnightly or weekly, which is what a tenant paid weekly would actually be offered at a counter. **`MAX_INSTALLMENTS` is still six and still a static form**; the split control makes the ceiling more visible, not higher. **The cap refusal is rendered per lease and so is `planCapFor`** — one extra query per lease on the profile, which is the same shape as `arrearsForLease` beside it and was not measured.
