### B-165 — A rule-based rate increase is a step, not a jump to street

`caccde5`

**What it built.** `targetRateFor` was one line — `return candidate.streetRateCents` — so a rule-based batch raised every eligible tenant the whole distance to street in a single letter: a tenant at $89 against a $145 street rate got a 63% increase, and nothing in the product could express anything else. It now takes a **per-facility ECRI policy**: `min(street, round(inPlace + clamp(inPlace × pct, minStep, maxStep)))`. Six new `Facility` columns (`ecriPercentBasisPoints`, `ecriMinStepCents`, `ecriMaxStepCents`, `ecriCapAtStreet`, `ecriMinMonthsSinceChange`, `ecriMinGapCents`), six controls on `/admin/settings` in the same item, and `ecriPolicyFor()` reading them for both the preview and the commit. `/admin/rate-increases` states the rule in the words of the settings that produced it, links to them, and the worklist gains **New** and **Change** columns showing the dollar step *and its percentage* per row.

**What it decided.**

**D-94 — 10%, floor $5, ceiling $30, capped at street, as the seeded default.** The owner's number, chosen explicitly rather than by the code's silence. Keeping the old behaviour as the default was rejected for the reason the row was raised: a facility nobody has configured must not send the letter that loses the cohort.

**The percentage is against the in-place rate, not the gap.** That is the number a tenant judges the letter by. The dollar **ceiling** is what actually bounds it — a percentage alone still compounds on a high rate, which is how $400 becomes a $40 step.

**The street cap is applied last.** After the clamp and after the rounding, so nothing downstream can carry a sitting tenant past what a walk-in would pay for the same unit today. `capAtStreet: false` exists and is off by default.

**The rate is rounded, not the step.** `$89.50 + $8.95` lands on `$98`, not on `$98.45`. Rounding the step would leave the half-dollar in place forever.

**A policy that cannot raise anyone drops the row.** A 0% step with a $0 floor produced a "increase" to the rate the tenant already pays; `previewEligibleIncreases` now filters `newRateCents > inPlaceRateCents` rather than scheduling a notice announcing that nothing changed.

**The eligibility rule stopped being a module constant.** `DEFAULT_ELIGIBILITY` was a parameter default no form could override — configurable-shaped and unreachable. It is now two columns with two controls, which is this codebase's own rule applied to the half that had no column at all.

**A real bug found along the way — a cross-suite promotion leak, fixed.** The first full sweep failed on `tests/inquiries-db.test.ts` → "reports no promotion when none is running", which passed in isolation. Cause: `candidates()` in `apps/web/lib/promotions/service.ts` loads **every** active promotion in the database and lets `evaluatePromotions` filter by `facilityIds` — and an empty `facilityIds` means *all facilities*. `tests/transfer-db.test.ts:1196` and `tests/invoices-db.test.ts:144` both created active promotions with no scope, so whichever facility another suite was quoting in parallel had a discount running. Both fixtures now carry `facilityIds: [facilityId]`; the production behaviour is correct and unchanged. This was latent, not introduced here.

**Test verification.** Full unit suite **3,643 passed, 8 skipped of 3,651** (219 files passed, 1 skipped), **exit 0**. Typecheck, lint, `next build` and `prisma migrate diff --exit-code` all clean. `tests/rate-increase.test.ts` replaces its single "raises to street" case with eight pinning the percentage, both clamps, the rounding and the cap in both directions. `tests/rate-increase-db.test.ts` gains three proving the *facility's* configured policy is what the preview uses — and its `afterEach` now restores all six columns, because the facility outlives every test in the file and a leaked 0% step reads as "no lease is eligible" rather than as a stale setting.

**Left behind.** **The one-off form is untouched** — a manager typing a figure is already an explicit decision, still gated by the notice period and the regional approval, and B-177 owns replacing its free-text Lease ID with a picker and adding a confirm step. **B-177 also owns rendering this rule in the batch *approval* preview**; it is stated on the worklist you schedule from, not on the pending-approval list an approver acts on, which is why that row sits after this one. **No preview of the second and third cycles** — the screen answers "what does this batch do", not "how long until this tenant reaches street"; deliberately not invented, since nothing asked for it.

### B-166 — A held rate increase has a way back: Re-notice

`64defdf`

**What it built.** D-88 blocks an increase whose notice provably did not arrive, and B-152 built the hold with **Cancel as its only control** — the row's own copy told the operator to "cancel this and schedule it again", which meant re-typing a lease id into a free-text form and re-deriving the delta by hand, per row, for a failure mode whose usual cause holds forty rows at once. `renoticeRateIncrease` clones a held increase at the same figures with a recomputed notice and effective date, cancels the held row, and links the pair through a new `TenantRateIncrease.renoticedFromId`. `renoticeHeldIncreases` does every held row at one facility in one press. `/admin/rate-increases` gains a per-row **Re-notice** beside Cancel, an **On hold for an undelivered notice (n)** panel with the batch, a line marking a row as a re-notice, and corrected help copy. `rate_increase_notice_undelivered` can no longer be closed by typing.

**What it decided.**

**The clone carries the original approval.** Same lease, same current rate, same new rate — the regional's sign-off still describes exactly what is about to happen, so re-noticing does not queue for approval again. This is the mirror of B-162's reasoning for cancelling an in-flight increase on a transfer: there the transfer *replaced* the figure the approval was given against, so it could not carry; here nothing replaced it. Which is why the rate is **re-checked**: if the lease rate moved while the increase was held — a retention save went through — the re-notice is refused and names both figures, because the approved delta no longer describes the tenancy.

**A clone, not a revival.** `noticeFailureReason` still is cleared by nothing and the held row is still terminal. Editing the held row's dates in place would rewrite what was served and when, and a served notice is evidence. Two rows, one attempt — `renoticedFromId` is what says so, `@unique` because a re-noticed row is cancelled in the same transaction and can never be re-noticed twice.

**"The clock restarts" is a statement about the period, not about the date.** The effective date is kept when a full notice period still fits inside it, and slides to the soonest legal date when the hold consumed the runway. `noticeDate = effectiveDate − noticeDays ≥ today` by construction, so the tenant always gets the whole period from the *new* notice. Most re-notices therefore keep the date the tenant would have been told about anyway, which is the right answer for the operator and for the tenant.

**Re-noticing to the address that bounced is refused, and the address is named.** Without this the batch button is a way to send forty notices to forty dead addresses, hold all forty a day later and raise forty fresh tasks — a loop that looks like work and gives nobody notice. The check compares each dead `Message.toAddress` for the notice event against the tenant's current contact for that channel. `no_send_record` has no address to have corrected and is allowed through: the pipeline skipped or matched nothing, and the second attempt is what finds out whether that is still true.

**`DEAD_MESSAGE_STATUSES` was exported from core rather than copied.** The verdict asks *whether* the notice arrived; the re-notice guard asks *which address it failed at*. Two copies would drift, and the drift would be silent — a status missing from the guard's copy lets a re-notice go straight back to an address that has already bounced.

**A task whose truth is a record's state cannot be closed by a note — a new `resolvedByAction` in the task catalog.** The proof gate asks for evidence and accepts typing as evidence, which is right for "what did you do about returned mail" and wrong here: the increase stays on hold whatever anybody types, so a completed row would mean the queue had *forgotten* about a held increase rather than that anyone had unheld it. `completeTask` refuses the type outright (not merely by the queue not rendering a form — the action is reachable with any task id), the card renders the sentence and a link instead, and the two things that genuinely move the record — a re-notice and a cancel of a held row — complete it themselves inside their own transaction, the way `move_out_request_review` already did. The href lives in the catalog so the view never switches on a `Task.type` string.

**The batch reports refusals by name, not as a count.** "3 of 5 re-noticed" and nothing else leaves the two rows anybody still has to act on looking done.

**Accessibility.** The Re-notice control is named after its subject (`Re-notice increase for {tenant}`, 2.4.6) rather than repeating one word down the column, and every outcome — including the still-bad-address refusal — is announced from `AdminForm`'s live region, which is mounted with the page rather than inserted on submit (4.1.3). Admin-only surfaces; `apps/web/app/(public)/accessibility/page.tsx` was re-read and nothing it claims changed.

**Test verification.** Full unit suite **3,653 passed, 8 skipped of 3,661** (219 files passed, 1 skipped), **exit 0**, and run twice. Typecheck, lint and `prisma migrate diff --exit-code` clean. Ten new tests: nine in `tests/rate-increase-db.test.ts` covering the refusal naming the address, the clone's figures/approval/link, the notice-period guarantee, the effective date sliding when the runway is gone, re-notice → notice → apply end to end, the task closing on both a re-notice and a cancel, the moved-rate refusal, the not-held refusal and the batch's split result; one in `tests/tasks-db.test.ts` proving a note cannot close the held-increase task.

**Left behind.** **No attempt counter.** The pair links, so a chain of three re-notices is walkable and the audit log answers "how many times did we try", but nothing renders "attempt 3" — deliberately not a second denormalised column for a sentence nobody asked for. **The refusal checks the address, not the address's health.** Correcting a tenant's email to a *different* address that is itself suppressed is allowed through and will hold again — the pipeline's own suppression check is what catches it, one night later. **No e2e spec**, same gap B-152 left: the held state and now the re-notice are asserted at the service layer only. **`renoticeHeldIncreases` calls the single-row path in a loop**, one transaction per row, like `approveBatch` and `cancelBatch` — right for a per-row refusal message, and it is a handful of rows in the realistic case.

### B-167 — Six fee types that could be configured and never charged

`9d64d3c`

**What it built.** `FeeType` has ten members and `/admin/settings` gives every one an editable, effective-dated schedule; repo-wide only `admin`, `late`, `nsf` and `transfer` were ever posted. So a unit left full of rubbish, a lock cut at the operator's cost and a damaged door were each a settings screen with no consequence, and the certified-mail and lien costs a Texas operator is allowed to recover never reached a cure quote. This adds one charge control — fee type, amount pre-filled from the facility's schedule and overridable, required note — on the tenant profile and on the move-out screen, a new `fees:charge` permission, and two automatic postings from the notice pipeline. `apps/web/lib/billing/fee-invoice.ts` is the one fee-invoice primitive all three callers now share.

**What it decided.**

**Posting a fee is its own permission, `fees:charge`, held from counter staff up.** Neither `tenants:edit` ("contact info, notes, documents") nor `payments:take` ("accept payments") describes putting money onto somebody's account, and stretching one of them would have made the next reviewer guess. Counter staff hold it because the person who cut the lock or walked the dirty unit is who knows the fee is owed.

**The authority ladder is measured against the DEPARTURE from the schedule, in either direction, against the existing fee-waiver limit.** Under-charging gives money away and is a waiver by another name; over-charging is discretion over a tenant's money in the direction that hurts them, which if anything wants a limit more. One symmetric rule, the ladder that already exists, and no new limit column: a counter staffer's $0 limit means "the facility's price, exactly", a manager can move it $50, a regional $250, an owner without limit. A fee type the facility has never priced is a departure from zero, so all of it needs waiver authority — the right answer for "charge a tenant something nobody has ever costed".

**A real bug found along the way, and it is why the migration exists.** `(Invoice.leaseId, periodStart)` was unique across every invoice kind. It is the RENT generator's idempotency key and was never anything else's, and unscoped it capped a lease at **one fee invoice per calendar day**: a move-out posting a cleaning fee and a damage fee on the same afternoon lost the second **silently** (`raiseFeeInvoice` swallowed the violation as "another run won the race"), and an NSF fee raised on a day that already had a late fee **threw**, since `assessNsfFee` has no such catch. Both were latent, neither was introduced here. It is now a partial unique index in raw SQL — `unique(leaseId, periodStart) where kind = 'rent'`, the same device as `reservation_one_held_per_unit`. Late fees lose nothing: `chargedSteps` reads back which ladder steps a lease has been charged from the fee line descriptions, which was always the real guard.

**Three copies of the fee-invoice shape became one.** Late fees, the NSF fee and this would have been three, each carrying the same paragraph about why a fee is its own `kind: 'fee'` invoice with a matching ledger entry. `raiseFeeInvoice` takes a transaction client because two of the three callers already have one open. **The NSF fee now emits `invoice.created`**, which it did not before — `invoice.created` has no comms rule, so no tenant is emailed anything new; it is a domain-event row that was missing.

**The `lien` cost posts after the notice's own claim is snapshotted, and never on a correction.** A notice that quoted a fee it was itself creating would be arithmetically self-referential and would read, to a tenant, exactly as badly as that sounds — so the cost joins the running balance from generation rather than the claim of the notice generating it. `claimForLease` sums open invoices plus uninvoiced ledger charges, so the cure quote and the next notice pick it up with no second calculation. A correction is the same notice said properly, not a second lien process; charging a tenant for our own typo is indefensible.

**The `certified_mail` cost posts in `recordNoticeDelivery`, not at either call site.** The hand-recorded route and B-083's `mailNoticeCertified` both pass through it, so one hook covers both and no third route can be added that silently eats the postage. Guarded on `deliveredAt` having been null, so re-recording a delivery corrects the proof without charging twice.

**Ended leases are chargeable, deliberately.** The walk that finds the damage happens after the tenant has gone, which is the single most common case this exists for.

**No new fee types and no free-text amount outside the ladder**, per the row. `admin`, `late`, `nsf` and `transfer` are deliberately NOT in the ad-hoc list: each already has exactly one automatic charger, and a hand-posted second one beside it is how a tenant gets two late fees for one late month.

**Test verification.** Full unit suite **3,671 passed, 8 skipped of 3,679** (220 files passed, 1 skipped), **exit 0**, and run twice. Typecheck, lint, `next build` and `prisma migrate diff --exit-code` clean. Eighteen new tests: `tests/fee-charges-db.test.ts` (12) on what a charge lands as, its waivability through the untouched `waiveFeeInvoice`, two fees on the same lease on the same day, and every rung of the authority ladder including the unpriced-fee case; six added to `tests/notices-db.test.ts` on the two incurred costs — including that the lien fee is *not* in the claim of the notice that created it but *is* in the cure quote from then on, and that a correction charges nothing.

**Left behind.** **A fee charged on an ENDED lease is not collected by autopay** — `collectDueInvoices` filters `lease.status in OCCUPYING_LEASE_STATUSES`, correctly, since a moved-out tenant's card should not be charged automatically; the move-out settlement and the final statement are what collect it, and a fee posted after a move-out completes leaves the tenant a second statement. **No approval workflow for an over-limit override** — it refuses and names the rank that could carry it, which is the same posture `waiveFeeInvoice` has had since B-047; the approval queue is still nobody's item. **The charge control is not on the walkthrough or unit board**, where a lock cut is also discovered — two screens was the row's scope. **`auction_cost` still has no automatic poster**: advertising and auctioneer costs are genuinely ad hoc, but the auction pipeline could post the ones it knows about, and nothing owns that. **B-168 still has to unpick the promotional recapture**, which is a raw `ledgerEntry` rather than a fee invoice — this item deliberately did not touch it, but `raiseFeeInvoice` is now the shape it should move onto.

### B-168 — A promotional recapture you can argue down without forgiving the arrears

`f661a45`

**What it built.** B-145 posted the recapture as a bare `type: 'charge'` ledger row, so `waivableFees` could not list it, `waiveFeeInvoice` could not void it, it never aged, it never dunned, and autopay never collected it. The only lever `CompleteMoveOutInput` offered was `writeOff?: boolean` — **all or nothing across the entire residual**, so forgiving a disputed $60 recapture also forgave $400 of genuine arrears under one reason code. It now posts through B-167's `raiseFeeInvoice` as its own `kind: 'fee'` invoice, and reducing or waiving it is a lever of its own with a reason code and the fee-waiver ladder behind it. `PromoRedemption` gains `recaptureChargedCents`, `recaptureWaivedCents` and `recaptureInvoiceId`, and the promotions report gains three columns off them.

**What it decided.**

**The authority is measured on the amount FORGIVEN, not the amount charged.** The discretion being exercised is the gap — the same rule B-167 settled for a fee override against its schedule, applied to the rule's figure here. It goes through `fee_waiver` rather than riding on `leases:move_out`, which every counter staffer completing a move-out already holds; without that, the term the business advertises could be given away at the desk by anyone.

**The reduction flows through the SETTLEMENT, not around it.** `previewMoveOut` takes the override and hands the reduced figure to `settleMoveOut`, so `amountDueCents`, the write-off threshold and the manager-override decision all see the same number. Subtracting afterwards would have left the screen demanding a manager for a debt that no longer existed.

**A reduction rewrites the sentence, and the sentence stays on the ledger row.** B-145's rule is that the ledger description — which is what the tenant's own statement renders — must not be a different form of words from the screen that got their consent. `raiseFeeInvoice` appends the invoice number to whatever it is given, so the full reason is passed as the ledger description, and `applyRecaptureOverride` extends it with "— reduced by $79.00" or "— waived in full". The figure and the words move together.

**Clamped to the ruled amount: an operator may forgive a recapture, never invent one.** Charging more than the promotion actually gave away would bill money nobody saved, which is the same reasoning `recaptureFor` already uses for refusing to bill back a discount that was never delivered. Over-charging is clamped rather than refused, and needs no reason, because nothing was forgiven.

**Three report columns, not one.** A minimum stay that bills $4,000 and **waives** $3,800 at the counter is not a term; one that bills $4,000 and **collects** $600 from tenants who have already left is a different failure. Charged and waived are stored on the redemption; collected is read through `recaptureInvoiceId` to the invoice's own `amountPaidCents`, because a decision and a payment are different facts. All three are **null on a redemption whose lease is still live** — "not decided yet" must not report as "recovered nothing".

**Its own audit action, `promo.recapture_reduced`.** Filed under `fee.waived` it would be one row among every waiver ever made, and the question it exists to answer — is the minimum stay real — could not be asked of it.

**D-89 is untouched.** A transfer still recovers nothing; there is nothing to reduce, and the existing test still says so.

**Test verification.** Full unit suite **3,678 passed, 8 skipped of 3,686** (220 files passed, 1 skipped), **exit 0**, and run twice. Typecheck, lint, `next build` and `prisma migrate diff --exit-code` clean. Seven new tests: five in `tests/move-out-db.test.ts` — the invoice's shape, date and line text plus its reachability by `waiveFeeInvoice`; a counter reduction recording both halves and its audit row; a full waiver leaving $400 of arrears **untouched**, which is the defect in one assertion; the three refusals (no reason, over limit, no authority) each leaving the lease open; and the clamp — and two in `tests/promo-roi-db.test.ts` wiring the redemption columns through to the report, including the null case. `tests/promo-roi.test.ts`'s empty-totals assertion had to grow the three new keys, which is exactly what that test is for.

**A fixture that had to change, and why it is worth naming.** `tests/move-out-db.test.ts`'s teardown deleted leases but never invoices, because until this item a move-out created none. It now does, so the FK held every lease down and seven tests failed at cleanup rather than at their assertion. The redemption is deleted first — it points at the invoice.

**Left behind.** **A write-off still leaves the recapture invoice open.** `writeOff` posts a `write_off` ledger entry for the whole residual and leaves every invoice behind it `open` — true of rent invoices since B-047 and now true of this one too. The ledger nets correctly and the invoice list does not, which is a pre-existing shape this did not widen and nobody owns. **The move-out screen does not re-preview as you type.** It is a server component, so the settlement shown is the ruled figure until you submit; the fieldset states the entitlement and what forgiving costs, which is enough to decide, but the total above does not move under your hands. **The report's date range still filters on when the promotion was REDEEMED**, not when the recapture happened, so a recapture billed this month against an eight-month-old redemption sits in that cohort — right for "is this promotion's term working", wrong for "what did we recover in March". **No partial payment of a recapture invoice is surfaced anywhere but the report.**

### B-169 — The backstop that could not reach the units it was built for

`7631936`

**What it built.** B-151's release backstop lived inside `runDelinquencyTimeline`, **after** the guard that returns `skippedNoTimeline` for a facility with no configured timeline — so the sites most likely to have locks stuck on ended leases were the only ones it could never reach. It is now its own nightly job step, `delinquency.stuck-overlocks`, unconditional on timeline configuration. The removal task's label stopped asserting a payment, the reason moved into a new `Task.detail`, the reconciliation list gained a `stuck_no_lease` state, and the units board says a lock-with-no-tenant is not rentable.

**What it decided.**

**A sweep, not the one-off repair the row asked for.** B-151's own reasoning — quoted back at it — is that a nightly job that fixes what it finds cannot be forgotten the way a script can. `releaseStuckOverlocks` is idempotent and runs every night, so its first run **is** the repair and there is nothing to remember to run twice.

**The backstop was moved, not copied.** Left in the engine as well it would be a second copy of one rule with two places to drift; the engine's `continue` now carries a comment pointing at the job and saying why it could not work from there.

**The label states the fact; `Task.detail` states the reason.** B-058 wrote "the tenant has paid" for the cure path and it was true of it. B-151 then raised the same task after a lease ended, after an auction sale and after an abandonment — so the card asserted a payment that had not happened on the two paths where the tenant most certainly had not paid, and a staffer walked out expecting a grateful customer. The type cannot know which of five reasons produced it; the caller always does. `Task.detail` is generic rather than overlock-shaped for the same reason B-115's `subject` was: this is the second instance of "a card with nothing on it that its own creator could have supplied".

**The sweep reads the lease's own `moveOutReason`** rather than saying a blanket "lease ended", so a lock left after an abandonment says so. `UnitOverlock.removalReason` records it on the lock itself — "was this removed because they paid, or because we sold their things" is a question the record has to answer without a join.

**`stuck_no_lease` is flagged immediately, not after 24 hours.** Every other mismatch on that screen is a staff member not having got there yet. This one is a unit that has fallen out of sellable inventory with nothing in any queue about it, and waiting a day to say so is the same silence the state exists to break. It sorts above `awaiting_removal`, and a lock whose removal HAS been asked for is not stuck — it is already visible and already ageing.

**The units board derives it from two facts it already had.** `status === 'overlocked' && !occupant` needed no fifth query: a unit reading `overlocked` with nobody in it is not a tenant behind on rent, and the board previously showed the ordinary delinquency badge for it. All three layouts (table, grid tile, mobile card) say it in words, linked to the removal task list.

**PRD 02 US-10 gained the acceptance criterion.** It had one requiring the minimum stay be *stated* on the lease (B-144's) and none requiring the consequence, which is how the sentence stayed silent through B-145 without anything going red.

### B-176 — The screen that sets a minimum stay now says whether anything enforces it

`cef567c`

**What it built.** `minStayMonths` is set on `/admin/settings/promotions`; `promoRecapturePolicy` is set on `/admin/settings`; neither screen mentioned the other. The promotions field hinted that the minimum stay "is stated on the lease and in checkout" and said nothing about whether anything is recovered, while the policy defaults to `none` — "Nothing — the discount is theirs to keep". An operator could therefore run a six-month minimum for a year in the belief it was enforced, and it was decoration. Three things close it: the field states the facility's **current** policy with a link to the setting; submitting a minimum stay at a `none` facility returns a confirm-and-echo step naming the consequence before anything is created; and any minimum stay the facility does not recover is appended with "· not recovered on early move-out" in the list.

**What it decided.**

**The operator's sentence lives beside the arithmetic, exactly as B-175's does.** `minStayEnforcementSummary` sits in `packages/core/promotions/recapture.ts` next to `minStayTermSummary` and `recaptureFor`, and the page hint and the confirm echo both read it. Two screens describing the same policy in two hand-written strings is the shape of the defect this row fixes, one layer up; and putting it there makes "assert the sentence beside the amount `recaptureFor` returns under that policy" the obvious test rather than a remembered one.

**The confirm step exists because a promotion cannot be edited after creation.** `createPromotion`, `setPromotionStatus` and `addPromoCode` are the only writers — there is no update path. So the operator who believes the term is enforced cannot correct it later, only end the promotion and start a new one, and the ordinary 3.3.4 reasoning about irreversible money settings applies exactly as it does to a tax component. The create form now says so in a line of its own, which was missing and read as a draft you could come back to.

**The confirm waits for a name.** `createPromotion` refuses a nameless promotion anyway, and echoing "(unnamed)" back is a confirmation of nothing — that refusal goes first, and the confirm is what the second submit meets.

**A per-row control is named by its row, not by its form.** The three status controls render once per promotion, so a rotor heard "Make live, Pause, End, Make live, Pause, End…" with nothing saying which promotion (2.4.6). Both the visible text and the accessible name now come from one `statusAction` helper, so they cannot disagree. The wrapping `AdminForm`'s `label` was carrying `${status} ${promotion.name}` — "active Summer Special", not a sentence — and it bought nothing either way: **no screen reader composes a form's label into its descendants' accessible names**, the rule stated in a comment on `task-complete-form.tsx`, the component created to fix this same defect on the task queues.

**`Field`'s `hint` is a `React.ReactNode` now.** A hint whose whole job is to point at the setting it depends on has to be able to carry the link there. `label` was already a node for the same class of reason, and the prop is still serializable across the server/client boundary.

Production build, typecheck (including `tsconfig.tests.json`), lint and `prisma migrate diff --exit-code` clean. ### B-177 — The rate screen names the tenant instead of asking for a cuid

`2fca73d`

**What it built.** Both money forms on `/admin/rate-increases` took a free-text **"Lease ID"** with the hint "From the tenant's lease page", while the eligible table directly above them already listed every tenant, unit and current rate and offered no action at all. So the workflow was copy a cuid, paste a cuid — and a mistyped one permanently reduced a **different** tenant's rate, with a reason code recorded against them and nothing between the paste and the commit. B-153 shipped that as its own named left-behind and B-166's re-notice made it worse by requiring the same paste again. Both forms now take a picker of the facility's occupying leases, the eligible rows carry links that prefill it, and both return a confirm step before anything is written.

**What it decided.**

**A native `<select>`, not a combobox.** Every option is a real lease with the tenant, the unit and what they pay now on it, so there is no id to mistype and nothing on offer that a rate change is illegal on — an ended lease is refused by both services, so listing one is offering a dead end. It is linear in units, which is marked with a `ponytail:` comment: a facility large enough for that to bite wants a typeahead over a search endpoint, not a longer `<select>`.

**The per-row links are plain links, and the prefill is a query parameter.** `?raise=<leaseId>&rate=129.00#oneoff-heading` and `?lower=<leaseId>#decrease-heading` — no client JS, no state to keep in sync, and the form still refuses everything the service refuses. A prefill is only honoured when it names a lease that is actually in the picker, so a `rate` cannot render into the form beside no tenant at all.

**The confirm echo is read from the database, never from the form.** The current rate is the figure the operator is being asked to agree the change *against*; echoing back a number the browser supplied would confirm whatever the page happened to be showing rather than what is true. The helper returns `null` when the lease is missing or belongs to another facility, and the action then falls through to the service, which owns that refusal's wording — the echo describes, it never duplicates a rule.

**Nothing pre-flights the service's own refusals.** A rate that is not higher, an effective date inside the notice period, or a lease that already carries a live increase are still reported after the confirm rather than before it. Re-checking them in the action is exactly the "screen refuses what the write accepts" drift B-174 fixed by moving both bounds into one function, and the alternative — a dry-run flag through both schedule paths — buys ordering for a case the prefilled defaults make rare.

**`confirmLabel` was added to the confirm state.** The button was hardcoded "Yes, add it", which is right for an append-only tax component and wrong here; it now reads "Yes, lower this rate". Naming the act is most of what the step is for.

**The retention-save section is gated on `credits:manual` at this facility.** It rendered for anyone who reached the page and was refused on submit. Hoisting the gate the service already applies is what lets the picker require one of the two authorities *at this facility* without turning a graceful refusal into an error page for a manager whose authority is at another site.

**Per-row controls are named by their row.** "Approve" and "Cancel" rendered once per increase with identical accessible names and identical styling side by side, so the rotor read "Approve, Cancel, Approve, Cancel…" and the destructive one was a row-misread away (2.4.6). Each now carries an `aria-label` with tenant and unit, Cancel is visually destructive, and the batch pair is named by what the batch holds ("Cancel 12 increases effective Sep 23, 2026"). The wrapping `AdminForm`'s label bought nothing — no screen reader composes a form's label into its descendants' names, the same rule B-176 applied to the promotions screen an hour earlier.

**Test verification.** Full unit suite **3,715 passed, 8 skipped of 3,723** (220 files passed, 1 skipped), exit 0; `tests/rate-increase-db.test.ts` run twice, 64 passed both times. Production build, typecheck, lint and `prisma migrate diff --exit-code` clean. Four new cases pin the picker: it offers the tenant, unit and current rate; it never offers an ended lease; it is reachable on the retention-save authority alone; and it refuses an actor holding neither.

**Left behind.** **No test on the confirm steps themselves.** They live in server actions behind `requireStaffActor`, which nothing in `tests/` currently stands up; the axe pass over `/admin/rate-increases` covers the screen but not the second submit. **The "Lower this rate" link only appears where the eligible table does**, which needs `rates:tenant_increase` — a manager holding only `credits:manual` reaches the same form through the picker, one section down. **`Field`'s `hint` became a `React.ReactNode` in B-176 and is used as one here**; no other caller has been converted, and none needs to be.

### B-178 — The fee question says what it charges, and its answer matches its value

`c349796`

**What it built.** The returned-payment control on the tenant profile was a dropdown headed "Charge the fee?" whose first option read "Yes — charge the configured fee" and carried the value `"no"`, because the field was named `waiveFee`. The displayed answer was the opposite of the stored one on the one screen where a bank return is recorded, and it never stated the amount. It is now `chargeFee`, yes/no, rendered from one table the action reads back — and the facility's own configured figure is in the option text. Where the facility has priced no returned-payment fee there is no control at all, only a sentence. Same session, same class: the refund form's cheque-number input renders only for a cheque refund, and the four screens that printed raw reason-code keys ("collections uneconomic") read an operator label map instead.

**What it decided.**

**Label and stored value live in the same row, in `RETURN_FEE_CHOICES`.** Nothing could have caught the inversion, because the words and the value it submitted were two unrelated expressions in the same JSX — one careless edit from waiving every returned-payment fee at the counter, silently and permanently. They are now one table in `lib/billing/reversals.ts`, beside `returnPayment` itself, and `waiveFeeFromForm` is what the action reads. The test is the coupling: the option whose label starts with "Charge" must be the option that does not waive.

**An absent field waives, never charges.** `waiveFeeFromForm` returns `true` for null and for anything unrecognised. That is the only safe default given the second half of this row — the control is not rendered when the facility has priced no fee, so the field genuinely is absent on that submit.

**No fee configured is a sentence, not a dropdown.** A control offering to charge nothing is a question with no answer, and answering it wrote a `feeWaived: true` audit context that reads identically to a deliberate waiver. The paragraph says what will happen instead.

**The amount goes IN the option, not in a hint beside it.** The amount is the decision this screen is taking. `{amount}` in the label is substituted at render from `scheduledFeeCents(facilityId, 'nsf')` — the same schedule `assessNsfFee` reads inside the transaction, so the figure shown is the figure that posts. Two facilities on one profile get their own price each, which is why it is a map keyed on the returnable payment's facility rather than a single lookup.

**The control is named after its subject.** "Returned-payment fee", not "Charge the fee?" (2.4.6) — the action is in the options. The outcome still announces through B-170's page-level region, which matters more here than on most forms: recording the return removes the payment from `profile.returnable`, so the row reporting the outcome is the row the outcome deletes.

**The cheque number renders only for a cheque.** It was permanently visible under a hint reading "Cheques only." — a field inapplicable four fifths of the time on a form that moves money, with the instruction to skip it delegated to a hint. `RefundMethodFields` is a small client component holding the method select and the conditional field, the same disclosure `ChargeFeeForm` uses and for the same reason. **The spelling stays "Cheque"** — the product-wide D-15 pass to "check" is B-182's, and doing half of it here would hide the rest from that row's grep.

**`REASON_CODE_LABELS` went to the source, not to the screen the row named.** The backlog names `move-out/page.tsx`, which printed `code.replace(/_/g, " ")`. Two more screens — `/admin/units` and `/admin/units/setup` — passed the same codes through `labelForStatus`, whose fallback sentence-cases but cannot know that `collections_uneconomic` is "Not worth collecting". One exhaustive `Record<ReasonCode, string>` in `packages/core/audit/actions.ts`, beside `REASON_CODES`, read by all four; `labelForStatus` is no longer imported by either units page. A new reason code now fails to compile until it has words, which is the property `PROOF_FIELD_LABELS` (B-170) has and the reason this is the same device.

**`WAIVER_REASONS` on the tenant profile was deliberately left alone.** It is a narrowed list with context-specific wording — "Duplicate charge", "Other (explain in the note)" — and collapsing it into the shared map would make both worse.

**Test verification.** Full unit suite **3,720 passed, 8 skipped of 3,728** (221 files passed, 1 skipped), exit 0. Production build, typecheck (including `tsconfig.tests.json`), lint and `prisma migrate diff --exit-code` clean. Five new cases in `tests/return-fee-choice.test.ts`: the label/value coupling, exactly one charging option and one waiving one, the amount present in the charging label, the absent-field default, and an operator label for every reason code with no underscores left in any of them.

**Left behind.** **No e2e on either form.** `profile.returnable` needs a succeeded payment with a posted ledger entry and `profile.refundable` needs one too, and the demo seed creates no payments at all — so neither section renders on a seeded database and neither is reachable from a spec without the unscoped mutation B-120 forbids. The unit test covers the coupling; the rendering is covered by nothing, which is exactly the route-versus-state gap **B-184** owns. **The audit context still records `feeWaived`**, so a no-fee facility and a deliberate waiver remain distinguishable only by `feeCents: 0` versus the absence of a choice — the control's disappearance is not itself recorded. **Nothing back-fills.** Returns recorded before this shipped carry whatever the inverted control submitted, and there is no report that would show which. **The tenant profile is still seventeen stacked sections** — that is B-181, which depends on this row precisely because it is about to hide these controls behind disclosures.

### B-179 — A returned payment offers the pay route, not a phone number

`646e34e`

**What it built.** `/portal/documents` listed a bounced payment with the sentence "Returned unpaid by the bank. This amount is owed again — please call us" beside an amount column still showing the full payment as though it had landed, while `PayNowButton` sat one tap away on the dashboard. The tenant was asked to queue on a phone line to do what the next screen does in three taps, and the only signal the money was owed again was a sentence contradicting the figure next to it. The row now names the returned-payment fee if one was charged, marks the amount **in words** as returned, and offers the same `/portal/pay` route the dashboard uses — with the **facility's** line via `phoneFor` as the secondary route rather than the org number.

**What it decided.**

**The fee is read from the audit log, because nothing else ties it to the payment.** `assessNsfFee` raises an ordinary fee invoice through `raiseFeeInvoice`; `Invoice` has no column pointing back at the payment that caused it, and the ledger entry it posts carries no `paymentId` either. The one record that connects them is the `payment.returned` audit entry, whose context has held `feeCents` and `feeInvoiceNumber` since B-146 — indexed on `(entityType, entityId)`, one query for every returned payment in the list. Matching on the line-item description instead ("Returned payment fee — …") would be guesswork, and this figure is what decides whether the tenant understands a balance thirty dollars larger than the payment they are looking at.

**The pay link carries no amount of its own.** `/portal/pay?lease=X` sums the whole ledger through `payableLease`, so the reversal *and* the fee are already in the figure it prepares — the link text shows that same balance rather than the returned payment's amount. A link offering to pay $129 against a $159 balance would be a third number on a screen whose whole defect was numbers disagreeing.

**A lease that cannot take an online payment gets the phone, not a dead link.** `payableLease` requires an occupying lease, so a moved-out tenant following the link would land on "We couldn't find that unit on your account" — and a settled lease on "there's nothing to pay right now". `portalPayments` resolves both conditions itself and returns `payableCents: null`, which is what selects the `CallLink` branch. The tenant who most needs an explanation is the one whose account has already closed.

**The state is on the figure, in words.** "$129 / returned" under the amount, not a strikethrough and not a colour (1.4.1). B-146 put the sentence in the date column and left the money column saying the opposite; the two columns now agree without either relying on the other being read first.

**The pay link is named by its unit.** Several returned rows would otherwise offer links reading "Pay $159 now" with nothing distinguishing them in a rotor (2.4.4/2.4.6); the `aria-label` adds "on unit 12" where the unit is known.

**The enrichment costs nothing on an ordinary list.** `returnedPaymentContexts` is passed only the returned rows and returns an empty map before issuing a query when there are none — which is nearly every tenant. The three reads it does make run in parallel, and the lease read is scoped by `tenantId` as well as by id, per this file's rule that a read never relies on an earlier one having been scoped.

**Test verification.** Full unit suite **3,724 passed, 8 skipped of 3,732** (221 files passed, 1 skipped), exit 0. Production build, typecheck (including `tsconfig.tests.json`), lint and `prisma migrate diff --exit-code` clean. Four new cases in `tests/refunds-db.test.ts`, in the file that already stands up a real returned payment: the fee named and the balance offered (with the facility's own phone, not the org line); zero fee reported when the return was waived, so the tenant is never shown a charge nobody made; `payableCents: null` when the reversal left the lease settled; and no return context at all on an ordinary payment. Run twice, 33 passed both times.

**Left behind.** **The returned row is a state no scan reaches.** `/portal/documents` is in `SCANNED_ROUTES` and is scanned on every push, but the demo seed creates **no payments at all**, so the axe pass covers the ordinary rows only and the new links have never been scanned in place. That is the route-versus-state gap **B-184** owns, and it is now named on the accessibility page rather than left to be inferred from a green run. **The bottom-of-page "Need a receipt? Call…" paragraph still uses the org line**, deliberately: it is about the whole list, and a tenant with units at two facilities has no single facility line to give. **Nothing tells the tenant *when* the bank returned it** — the row still shows the date the payment was taken, which is the date on the receipt they hold, and the return date is not surfaced anywhere on the portal.
